# 实现 0x19 / 0x14 DTC：先想清楚「不做持久化」才敢动手

- 日期：2026-11-05
- 类型：功能 / 决策
- 关键词：`uds` `dtc` `0x19` `0x14` `ram-only` `nrc-0x14`
- 验证等级：主机模型（TinyCC，两套容量），**无实机、无真实 CAN/UART 链路**

## 1. 一句话

给 ECU 加了 `0x19` 读 DTC 与 `0x14` 清 DTC，表放 RAM（8 条），四类 DTC 全部由真实失败路径写入，回归从 3328 涨到 3385。

## 2. 背景与约束

任务清单里 T9 一直挂着「未实现」，11-05 全量复核也确认：全仓 `grep -rn dtc/DTC` 零命中 —— 没有结构、没有存储字段、没有状态掩码。所以这不是「补两个 `case`」，第一步必须先把存储方案定下来。

约束：
- `src/core/metadata.c` 的双副本 + 序号 + CRC + commit 末写不得简化，`src/core/` 不得引入 HAL。
- `boot_context_t` 里只有 `store`（`metadata_store_t`）和 `external`（`flash_port_t`），**没有 `eeprom_port_t`**。
- 数字只用当场实测；主机模型 / 目标构建 / 实机不能混称。

## 3. 现象

失败的升级不留任何痕迹：每条错误路径回一个 NRC 就把事情忘了。tester 无法区分「根本没试过」和「上次试过但包校验失败」——而这正是 OTA 现场最重要的信息。

## 4. 排查过程

| 步骤 | 我怀疑什么 | 做了什么 | 结果 |
|---|---|---|---|
| 1 | 是不是只要加两个 case | 全量枚举 `uds.c` 分派 | 不是。`handle_read_data` / `handle_request_download` / `handle_transfer_exit` / `handle_routine` 各自直接 `return nrc_reply(...)`，没有任何记录点 |
| 2 | DTC 能不能持久化 | 查 `boot_context_t` 与 `metadata_t` | 不能顺手做。上下文里没有 `eeprom_port_t`，持久化必须扩 `boot_context_t` 或复用 `metadata_t`，而后者是「双副本+序号+CRC+commit 末写」的核心约束对象 |
| 3 | EEPROM 有没有空闲区 | 算 AT24C02 布局 | 有 128 B（64–127、192–255），但那是第二步的事，不该为诊断服务先动核心存储 |
| 4 | 0x14 的 groupOfDTC 怎么读 | 写完第一版测试跑红 | **踩坑**：用 `get_be32(&req[1])` 多读了 `req[4]`，合法的 `14 FF FF FF` 全被拒成 `0x31`。group 是 **3 字节** |
| 5 | 为什么清 DTC 一直失败 | 打印 ECU 实际收到的字节 | **踩坑**：`dtc_count()` 会覆写 `req[0..2]`，之后手拼的「清除请求」实际发出去是 `19 01 FF FF`，ECU 正确回了 `7F 19 13`。产品代码没错，是测试的请求构造方式错了 |

## 5. 根因

两个都是「就地改共享缓冲区」的经典毛病：测试里 `req[]` 是文件级共享状态，一个只改前三个字节的辅助函数会污染下一次请求；实现里 `get_be32` 假定 4 字节字段，而 `groupOfDTC` 是 3 字节。两者都不会编译报错，只会让断言在远处莫名其妙地红。

## 6. 修复

**存储决策**：RAM 表放 `uds_server_t`（`uds_dtc_t dtc[8]` + `dtc_count` + `dtc_dropped`）。刻意不持久化，理由写进头文件注释：持久化要动 `metadata.c`，一个诊断服务不值得。表满时保留最旧的 8 条、把丢失数记进 `dtc_dropped`，而不是静默覆盖。

**服务**：
- `0x19` 子功能 `0x01`（数量，DTCFormatIdentifier `0x01` = ISO 14229-1）与 `0x02`（按状态掩码列 `[status, DTC hi, mid, lo]`），支持 SPRMIB。
- `0x14` 只接受 `FFFFFF`，其它组回 `0x31`；长度不对回 `0x13`。
- **容量先算**：`3 + 4 × count` 放不下就回 NRC `0x14`（responseTooLong），绝不截断、绝不越过 `resp[max]` —— 与刚合入的 `0x22` 修复同一条规则。
- 状态位只实现 4 个（testFailed / thisCycle / confirmed / failedSinceLastClear = `0x2B`），availabilityMask 也报 `0x2B`，不假装支持没实现的位。

**四个记录点**（都能在测试里真正触发，不是只写了调用）：
| DTC | 含义 | 触发路径 |
|---|---|---|
| `0xC10400` | 安全访问 | `0x27` 连续 3 次错密钥 → 锁定 |
| `0xC10300` | 元数据 | `0x34` / `0x37` 的 `metadata_load` / `metadata_save` 失败 |
| `0xC10100` | 外部 NOR | `0x34` 擦除失败、`0x36` 写失败 |
| `0xC10200` | 包校验 | `0x37` 与例程 `0001` 的头/CRC/签名拒绝 |

## 7. 验证

全部当场实测，TinyCC 主机模型：

- 红（服务未接线，只留 API 桩）**3348 checks / 37 failures** → 绿 **3385 / 0**，1024 KiB 与 512 KiB 两套容量数字一致。
- 420 个存储断电模型场景不变。
- 四道独立闸门：`-fanalyzer` 10 文件 0 诊断；`-Wall -Wextra -Werror` **25** 文件 0 诊断（新测试文件进闸门）；host suite 3385/0；python unittest 28/0。
- `verify_project.py` 全量重刷 **84.7 s**、`status=passed`、**130** 个源码哈希、7 项 virtual CAN、四套 GNU 只读镜像链接通过。
- `hardware_verified=false`、`keil_target_linked=false` **未变**。

## 8. 学到了

1. 做诊断功能，第一个要定的不是报文格式，而是**「故障记在哪、掉电还在不在」**。理由写进注释，比写在 commit message 里活得久。
2. 「响应放不下」这条规则一旦定成 NRC `0x14`，所有新服务都得遵守；这次直接复用了同一个常量，没有再发明一遍。
3. 测试里共享的请求缓冲区是雷。**请求应该由构造器整条生成**，不要「改几个字节再发」。
4. 红态数字要干净：第一版红里有 9 条是测试自身缺陷，不能拿去当「修复前证据」；重新退回到未接线状态测一次，才得到 3348/37。

## 9. 简历表述

> 为 STM32 OTA ECU 实现 UDS 诊断服务 `0x19`/`0x14`：设计 8 条 RAM DTC 表与状态掩码过滤，把安全锁定、元数据读写、外部 NOR 擦写、包校验四类失败接入记录路径；响应容量不足时按 ISO 14229-1 返回 NRC `0x14` 而非截断，并用带哨兵的边界用例验证不越界。主机模型回归 3385 断言 × 2 容量全过。

## 10. 边界

- **未持久化**：掉电即清空，测试里专门有一条断言证明这个易失性，防止有人误当成掉电保留。
- **未上真实链路**：`0x19` / `0x14` 没在真实 CAN 或 UART 上跑过，`hardware_verified=false`。
- **子功能只做了 `0x01`/`0x02`**：`0x04`（快照）、`0x06`（扩展数据）、`0x0A`（支持的 DTC）都没做。
- **PC 工具没有 DTC 页**：`uds_gui.py` / `uds_tool.py` 还不能点这两个服务，实机验证前得先加。
