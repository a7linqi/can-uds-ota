# 给恢复协议加"范围恢复"：一次写坏→修回从 87 分钟降到 77 秒

- 日期：2026-11-05
- 类型：功能 / 工具
- 关键词：nor-restore, swd-mailbox, range-restore, spi-nor, w25q128, evidence
- 可写进简历：Y

## 1. 一句话

在已有的 SWD RAM mailbox 恢复协议上加了一条 `0xA3000000` 范围恢复命令，只重写受影响的
32 KiB 块，实机实测"写坏一块 + 全片扫描"共 77 s，而整片 16 MiB 恢复要 5236 s，相差 67 倍。

## 2. 背景与约束

T5 起要真正通过 UDS `0x34/0x36` 写外部 NOR，而 `DOWNLOAD_OFFSET = 0`，写进去的第一批字节
正好压在金标镜像（原厂 16 MiB 内容）头部。数据本身不怕丢：11-03 有两份全片备份，
11-05 又用 512 块演练证明整片恢复能逐字节复原（器件 CRC32 `0xA4188821` = 金标）。

问题在**代价**：整片恢复一次 5236 s（87 分钟）。若每次写实验都要等 90 分钟才能回到已知状态，
下一步的合理选择就变成"先不恢复，接着做"，而这正是把"可回滚"变成口号的典型走法。
所以先给恢复工具加定向能力，再动真写。

约束：不能动产品源码（`src/core` 冻结），只能改 board-lab 的恢复固件与主机工具；
不能破坏已验证的整片恢复路径（420 个断电场景、512 块演练都建立在它上面）。

## 3. 现象

`nor_restore.py --hardware` 只有两个模式：整片恢复（0 → 16 MiB）和只读全片核验。
状态机的 DONE 判定写死 `offset == total`，CRC 也写死整片 CRC，因此"只恢复第 N 块"
这件事在协议层根本无法表达——不是主机少个参数，是设备侧没有会话边界这个概念。

## 4. 排查过程

第一版想法是"让主机只发目标块，设备从 0 开始等"。走不通：设备的 `NR_S_READY`
要求 `mb->h.offset == c->offset`，而 `c->offset` 只会从 0 递增；跳过前面的块会被判成
`BAD_REQUEST`。除非把前 511 块也发一遍——那又回到 87 分钟。

第二版想法是"编译一份 total = 32 KiB 的恢复固件"。能work，但只覆盖块 0，
换一块就得重编重烧，而且 `hardware_gate()` 的构建记录绑定会被反复刷新，
等于每次实验都在改"证据链的锚点"。放弃。

第三版：给协议加第三条命令，把范围放进**已有的** `offset`/`length` 字段。
检查过时序：设备在 `NR_S_WAIT` 里只认 `ack`，所以主机可以先写 `offset`、`length`，
最后才写命令字 `ack`，设备真正读这两个字段时它们已经稳定——不需要新字段，
也就不会破坏 40 字节头的兼容性。

## 5. 根因

恢复状态机的"会话边界"被硬编码成"整个芯片"：`total` 同时承担了三个语义——
数据总量、循环终止条件、以及 DONE 的验收常量。三种语义混在一个字段里，
所以任何"只恢复一部分"的需求都无处安放。

## 6. 修复

固件（`stages/board-lab/firmware/nor_restore.{c,h}`）：

- `ctx` 增加 `start` / `end`，把"循环从哪开始、到哪结束"显式化；`total` 退回只当容量上限。
- 新命令 `NR_CMD_RESTORE_RANGE = 0xA3000000`。`begin()` 在**清零请求字段之前**读
  `offset`/`length`，校验：`start < total`、`start % 4096 == 0`、`length % 4096 == 0`、
  `length > 0`、`length <= total - start`。任一条不过就 `ERROR/BAD_REQUEST`，一个扇区都不擦。
- 块校验从 `offset + length > total` 收紧为 `> end`，块不能越出会话边界。
- `COMMIT` / `FINAL_CRC` 改用 `end`，DONE 发布 `offset = end` 与**范围** CRC。
- 整片恢复和只读核验走 `start=0, end=total`，代码路径完全没变（这是刻意的：改行为不加分支，
  只把常量换成变量）。

主机（`host/nor_restore.py`）：

- `Driver.restore_range(data, start)`：同一套 submit/confirm 握手，只是起点不同。
- `--block N` / `--block-count K` / `--verify-full`。`--verify-full` 会在范围恢复后
  **复位**再做一次全片 CRC 扫描（范围会话 DONE 后状态机不再接受新命令，必须重开上下文，
  这同时让扫描读的是硅片而不是残留状态）。
- 模拟侧新增 `run_sim_range()`：芯片以金标镜像为种子、**只把目标范围抹成 0x00**，
  所以"范围恢复通过"等价于"目标范围修好且其余字节一个没动"。

## 7. 验证

主机（无硬件）：

- C 状态机测试 12 项全过，新增两项：范围恢复只擦自己那两个扇区、邻居保持 0xA5 哨兵值、
  DONE 发布范围 CRC 与 `end`；越界/未对齐的范围被拒且 `erase_calls == 0`。
- `--selftest` 6 项：整片 happy path、整片断电重试、只读核验、范围恢复、范围断电重试、
  设备拒绝越界范围。
- 聚合检查 `tests/run_restore_checks.py` 全过，含 16 MiB 金标模拟恢复，CRC `a4188821`。

实机（2026-11-05，证据 `stages/board-lab/evidence/nor-range/`）：

| 步骤 | 结果 |
|---|---|
| 故意写坏块 0（填 0x5A） | 11.0 s，器件范围 CRC `0xBFBAD03B` = 篡改块 CRC |
| 全片扫描 | 器件整片 CRC `0x7660036E` = 篡改镜像 CRC，66.2 s |
| 金标恢复块 0 | 10.95 s，范围 CRC `0x830246CC` = 金标块 0 CRC |
| 复位后全片扫描 | `0xA4188821` = 金标，`full_chip_crc_match=true` |

第 2 步是这次的关键：整片 CRC 与篡改镜像逐字节相等，说明"写坏"真发生在硅片上；
第 4 步同一块芯片只重写一块就回到金标，说明范围恢复不是"看起来成功"。

## 8. 学到的东西

- **把验收常量换成会话边界，整片模式就退化成 `start=0, end=total` 的特例**。
  这比"加一个 if 分支"安全得多：老路径的行为不是被保留，而是根本不存在第二条路径。
- `ctx` 结构一改，`nor_restore_mailbox` 的链接地址就从 `0x200003B0` 变成 `0x200003B8`。
  第一次上板我用旧地址，被 `hardware_gate()` 直接拒掉（`mailbox address 0x200003b8 != 0x200003b0`）。
  闸门在这一刻的价值是"挡住一次打错地址的写入"，而不是流程仪式。
- 恢复手段的成本决定它会不会被真的使用。"有备份"不等于"敢实验"，中间差的是恢复时间。
- 主机侧“写坏”也要用产品同款路径（erase + program + 读回校验），否则修好的证据是假强。

## 9. 简历表述

给 SWD 调试恢复协议增加范围恢复命令（自定义 RAM mailbox + 会话边界），把单块修复从
整片 16 MiB 重写 5236 s 降到 77 s（67×）；以"故意写坏 → 全片 CRC 比对 → 定向修复 →
复位后全片复查"的 A/B 流程在 STM32F407 + W25Q128 实机验证，并保持整片恢复与 420 个
掉电场景的既有行为不变。

## 10. 边界与未解决

- 范围恢复只解决"把已知内容写回去"，不解决"判断哪一块坏了"——那要靠产品侧元数据/CRC。
- 断电只在模拟器里验证过（范围会话中途掉电 → 重启重跑收敛），**没有真实拔电**。
- 实机只覆盖块 0（32 KiB），多块与跨 4 KiB 扇区的边界仅由模拟与 C 测试覆盖。
- T5 仍未开始：UDS `0x34/0x36` 的真实擦写还没发生，`hardware_verified` 的产品侧字段仍为 false。
