# 定死 512 块演练停在 478 的根因：设备比主机的一次读还快

- 日期：2026-11-05
- 类型：缺陷 / 决策（推翻旧判断）
- 关键词：`nor-restore` `swd-mailbox` `race` `ack` `cube-programmer`
- 验证等级：**实机**（探针与 3 块短程）+ 主机模型（模拟回归）

## 1. 一句话

昨晚停在 477/512 不是 `ack` 被吞、也不是写入失败，而是**设备做完一块只要约 0.8 秒，主机的一次确认读却要 0.875 秒**；读完时 status 已经是 `BLOCK_OK`，`_confirm()` 只接受 `{BUSY, DONE}`，于是把"做完了"判成"没接受"。

## 2. 背景与约束

2026-11-04 23:20 整片恢复演练在第 478 块提交时失败，报 `device did not take the command at block 478 submit (status 0x3)`。当时已用两条独立证据证明**数据无损**：477 条事件逐块 CRC 与金标 0 处不一致、独立只读核验器件自算整片 CRC `0xA4188821` = 金标。所以问题被限定在握手层，但具体机制没定死，留下两个互相矛盾的假设：

- 假设 A：`NR_S_COMMIT` 无条件 `mb->h.ack = 0u` 吞掉并发门铃；
- 假设 B：写 `ack` 的 CLI 异常被 `tolerate=True` 静默吞掉，字根本没写进去。

昨晚发现"写门铃到读头只差 0.877 秒，而一块要 10 秒，ack 却已是 0"，据此认为 A 解释不通。用户明确要求：这个矛盾没解开前不要盲目重跑 85 分钟。

约束：不改固件、不重烧（板上固件已通过构建绑定校验）；改主机脚本必须保留 CRLF；数字只用当场实测。

## 3. 现象

失败瞬间邮箱头（`hdr-...-04346.bin`）：
`session=0x26d777ec seq=0x1de(478) offset=0xEE8000 length=0x8000 crc32=0xf4f47777 status=0x3 ack=0x0`。

CLI 事件显示最后 5 次 `-w32` 全部 `returncode=0`，最后一次把 `0x1de` 写到 `0x200003d4`（`OFF_ACK`），日志里有 `32-bit data download complete`。

## 4. 排查过程

| 步骤 | 我怀疑什么 | 做了什么 | 结果 |
|---|---|---|---|
| 1 | 假设 B：ack 没写进去 | 读 `cli-events.jsonl` 最后 8 条 + `04345` 日志全文 | 地址/值/返回值全对，**B 排除** |
| 2 | "0.877 秒不可能做完一块"这条推理本身 | 逐字段算时间戳 | 写结束 `23:20:36.439`，读开始 `23:20:36.450` —— **间隔只有 11 ms，0.877 s 是读头命令自己的耗时**。昨晚把 duration 当成了等待间隔 |
| 3 | 固件清 ack 的时机 | 通读 `firmware/nor_restore.c` | READY 收到 `ack==seq+1` 立即 publish `BUSY`；只有 COMMIT 才 `ack=0` + `BLOCK_OK`。固件侧不可能在受理瞬间清 ack |
| 4 | 设备到底多快 | 写单块上板探针：复位→arm→提交金标第 1 块→连续读头 | `BUSY/ack=1` → 约 **0.8 s** → `BLOCK_OK/ack=0`，**设备做完一块只要零点几秒** |
| 5 | 为什么偏偏第 478 块 | 对比本次探针读头 0.14 s 与昨晚末期 0.875 s | 长跑后 CLI 变慢；当读头耗时超过设备处理时间，这一次读就横跨整个 BUSY 窗口，回来时已是完成态 |

**转折点**：第 4 步。探针把"设备快 / 主机读慢"从推测变成可核对的时间序列，假设 A 和 B 同时被推翻 —— 真正的问题是主机把一次**慢读的结果**当成了**提交瞬间的状态**。

**弯路**：第一次修 `set_u32` 时，我按"既然用了 `-nv` 就不会有回读校验"的假设，把容忍条件收紧成"日志必须出现 `32-bit data download complete`"。结果短程验证第一步就失败：CLI `exit 1: b''`。打开日志才看到

```
w @0x200003d4:  0xa1000000
Error: Failed to download data! ...
```

**`-nv` 在 CubeProgrammer 2.23.0 上并没有抑制 `-w32` 的回读校验**；固件一收到命令就清 `ack`，回读必然不符。原来的 `tolerate=True` 是必要且正确的，我把它改坏了。判据随后改成"日志证明本地址本值已发出 **且** 错误正是已知回读不符"，其余异常照旧抛。

## 5. 根因

`Driver._confirm()` 提交后只读一次头，且 `accepted={ST_BUSY, ST_DONE}` 不含 `ST_BLOCK_OK`。设备处理一块约 0.8 s，晚期一次读头 0.875 s，读回来时设备已完成并清了 `ack`，status=`0x3`。主机把完成态当成"命令没被接受"而中止。端到端的 10 s/块里绝大部分是 SWD 传 32 KiB 的 8.9 s，把"10 秒"误当成固件侧耗时是整条错误推理的起点。

## 6. 修复

全部在 `stages/board-lab/host/nor_restore.py`，**固件与板上镜像一字未改**：

- `_confirm()`：改成带 10 s 超时的循环，要求**连续两次读一致**才判定（顺带排除 40 字节头撕裂），并把 `BLOCK_OK + ack==0`（设备已完成）纳入接受集；`ST_ERROR` 与断电场景照旧立即抛。
- `set_u32()`：宽容判据收窄到"日志里有本地址本值 + `Failed to download data`"，连接失败/超时不再被静默吞掉；同时把 `-nv` 无效的实测结论写进注释。
- `finish()`：DONE 头读两次比对，拒绝混合快照（对应 11-04 三次 verify 两次 `offset=0x1000000`、一次 `0x0`）。

备选方案与放弃原因：改固件让 COMMIT 写 `blocks_done` 计数或保持 BUSY 直到主机确认。放弃，因为要重烧镜像、重做构建绑定，而最终验收本来就有**器件自算整片 CRC 与金标比对**（`match = info["device_crc32"] == expected_crc`）作为硬兜底，握手层的假通过不可能伪装成 `passed`。

## 8. 学到的东西

1. 日志里的 `duration_s` 是**命令自身耗时**，不是两次命令之间的间隔。把它读错，会推出一个根本不存在的"物理上不可能"。
2. "端到端耗时"不等于"设备侧耗时"。SWD 传 32 KiB 占 8.9 s，固件擦写只占约 0.8 s，两者混为一谈会直接误导根因判断。
3. 一次性判别读 + 白名单状态集合，是典型的时序竞态配方：设备比读操作快时，"已完成"会被当成"未受理"。
4. 不要凭参数名猜工具行为。`-nv` 看起来像 no-verify，实测对 `-w32` 无效；收紧容错之前先看一眼真实日志。

## 9. 简历表述

> 定位并修复 SWD 邮箱握手的时序竞态：用单块硬件探针测出设备完成 32 KiB 块仅需约 0.8 s、而晚期一次读头需 0.875 s，据此把"一次读 + 固定状态白名单"改为"双读一致 + 接受完成态"，并收紧 CLI 异常容错；模拟 512 块恢复与真机短程验证均通过，固件与板上镜像零改动。

> 全程以器件自算整片 CRC32 与金标比对作为最终判据，主机侧误判不会伪装成升级成功。

## 10. 边界与未解决
