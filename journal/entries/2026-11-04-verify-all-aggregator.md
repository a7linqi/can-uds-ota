# 把五项自检收成一条命令，并反证它真的会红

- 日期：2026-11-04
- 类型：功能
- 关键词：`self-check` `verify_all` `negative-control`
- 验证等级：主机模型

## 1. 一句话

`static-check`、三个合并包、三包合并验证分散在五个入口，一键汇总成 `verify-all.cmd`（27.2 秒），
并用构造的失败命令证明这个聚合器不是又一个"永远为绿"的假保护。

## 2. 背景与约束

到这一轮，`build-temp/` 里已经有五个各自独立的自检脚本，每个都有自己的入口和输出格式。
问题不在于它们不准，而在于**没人会每次都手动跑五个**——今天已经吃过一次亏：
`-fanalyzer` 因为配了 `-fsyntax-only`，安静地空跑了很久，谁都没发现。
约束照旧：不动产品仓库，只在 `build-temp/`。

## 3. 现象

五个入口各自为政：

| 入口 | 耗时 |
|---|---|
| `static-check/check.cmd` | 8.9 s |
| `isotp-stmin-package/verify.py` | 8.6 s |
| `metadata-page-package/verify.py` | 0.3 s |
| `uds-nrc-package/verify.py` | 8.5 s |
| `merge-proof/build.cmd` | 2.2 s |

逐项单独测得的耗时相加是 28.5 秒（含 `.cmd` 包装与 `pause` 开销），
但真正的问题不是秒数，而是要记住五条路径、五种输出。实际上没人会做。

## 4. 排查过程

| 步骤 | 我怀疑什么 | 做了什么 | 结果 |
|---|---|---|---|
| 1 | 直接串 `check.cmd` 会卡住 | 看它的结尾 | 有 `pause`，从 Python 调用会挂死 |
| 2 | 换调用目标 | 改调底层的 `check.py`（`check.cmd` 只是包装） | 不挂 |
| 3 | 汇总脚本会不会永远为绿 | 用 `-c "raise SystemExit(1)"` 替换掉真实检查 | 正确返回 1 |
| 4 | 反过来会不会永远为红 | 只放一个必然成功的命令 | 正确返回 0 |

**转折点**：第 3 步。写完聚合器，第一反应是"跑一遍全 PASS 就完事"。
但今天刚踩过 `-fanalyzer` 空跑的坑 —— 一个只会输出 PASS 的脚本和空跑没有区别。
于是把检查表换成必然失败的命令，确认它真的会把红传播出来。

## 5. 根因

（这是新增功能，不是缺陷。本节记录设计选择。）

聚合器最容易犯的错是吞掉子进程的退出码：`subprocess.run(...)` 不看 `returncode`、
或者外层直接 `print("ALL PASSED")`。两种写法都会让"有一条挂了"和"全过了"看起来一样。

## 6. 修复

- 文件：`build-temp/verify_all.py`
  - 检查表是数据（`CHECKS` 列表），不是硬编码流程，便于被反向验证替换
  - 只认子进程退出码，不看输出里的 "PASS" 字样
  - 失败时把该子进程输出里含 `FAIL` / `MISMATCH` / `error` 的行打出来
- 文件：`build-temp/verify-all.cmd`（双击入口，纯 ASCII —— 含中文的 .cmd 会被 cmd 按 GBK 解析搞乱）
- 备选方案与放弃原因：把所有断言搬进一个巨型测试文件。放弃原因：
  三个包验证的是"补丁前后差异"，需要多次编译同一套代码，塞不进单一进程。

## 7. 验证

```
python build-temp/verify_all.py           # 27.2 s
python build-temp/verify_all.py -v        # 附每项完整输出
```

| 项 | 期望 | 实际 |
|---|---|---|
| 五项全跑 | 全 PASS | 全 PASS，**27.2 s** |
| 混入一个 `exit 1` 的命令 | 返回 1，表格里标 FAIL | 返回 1，`fails with rc=1 \| FAIL` |
| 只放必然成功的命令 | 返回 0 | 返回 0 |
| 双击 `verify-all.cmd` | 不卡、不乱码 | 正常 |

未验证：不覆盖实机与目标构建（那两项本来就要板子和交叉编译器，不在主机自检范围内）。

## 8. 学到的东西

1. **聚合型自检必须自带反向验证。** 它最容易骗人，因为它看起来什么都没做却给了绿灯。
2. 判断脚本成功与否只能看**退出码**，不能看输出字符串 —— 否则子进程崩了而输出里恰好有 "PASS"，
   聚合器就会说谎。
3. `index.md` 式的入口清单会腐化；把入口收成一条命令，比写更详细的文档有效。

## 9. 简历表述

> 将分散的主机侧自检（静态分析、四组边界回归、三包合并验证）收成一个 27 秒的单入口脚本，
> 并用构造失败命令反向验证聚合逻辑，避免出现"永远为绿"的假保护。

## 10. 边界与后续

- 不含实机与目标构建，那两项需要板子（SWD 当前被 NOR 演练占用）和交叉编译器。
- 三个包仍是未合入状态，`verify_all.py` 证明的是"补丁能干净合并且不破坏断言"，不是"已合并"。
