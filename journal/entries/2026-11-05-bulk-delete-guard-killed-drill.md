# 512 块演练卡在 49：每块删一个临时文件触发了宿主的安全删除守卫

- 日期：2026-11-05
- 类型：环境 / 缺陷
- 关键词：`safe-delete` `bulk-delete` `long-running` `scratch-file` `tee`
- 验证等级：实机（中断现场）+ 实机短程（修复后 3 块）；**全程重跑结果待填**

## 1. 一句话

握手修复后的第一次 512 块演练在 **49/512** 被环境的批量删除守卫终止；根因是 `put_data()` 每块 `tmp.unlink()` 一次，累计到第 50 次删除触发确认阈值。改成全程复用一个临时文件、零删除后重跑。

## 2. 背景与约束

板子已连、握手根因已修、真机 3 块验证通过，08:24 启动 512 块全程演练（预计约 85 分钟）。演练必须留下 `manifest.json` + 512 条 `events.jsonl` 才算证据；只有进程退出不算。

约束：不改固件、不重烧；长任务在后台跑，人不在电脑前；脚本写在 `build-temp/` 避免破坏 `hardware_gate` 的 `stage_hashes` 绑定。

## 3. 现象

后台任务报 `completed with exit code 0`，但日志尾部是：

```
[  49/ 512]   9.57%   496.3 s  ETA  78.2 min  3.15 KiB/s
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":50,"threshold":50,"scope":"turn","targets":["...blk-254f5dc44df9-00493.bin"],"targetCount":1}
```

证据目录 `evidence/nor-restore/20261105_082401_562737/` 里 **`manifest.json` 不存在**，`events.jsonl` 只有 **49 行**，目录里 691 个文件。

## 4. 排查过程

| 步骤 | 我怀疑什么 | 做了什么 | 结果 |
|---|---|---|---|
| 1 | 演练成功了 | 看到后台任务 `exit code 0` | 差一点直接去报喜；但 `tee` 在管道末端，它的 0 **不代表 python 的退出码** |
| 2 | 也许只是日志缓冲 | 读 `manifest.json` 与 `events.jsonl` | manifest 完全没有，events 49 行 —— **确认中途死亡** |
| 3 | 板子 / SWD / 固件出问题 | 看最后一条正常进度与守卫报错 | 第 49 块正常完成；守卫打印的是**删除**确认，不是 SWD 错误 |
| 4 | 哪里有删除 | `grep -n "unlink\|remove\|rmtree" host/nor_restore.py` | 只有 `put_data()` 的 `tmp.unlink()`，每块一次，49 块后第 50 次正好撞上阈值 |
| 5 | 残留进程占着 SWD | 查两个 `python.exe` 的命令行 | 都是 fundval 项目的 Django `runserver 127.0.0.1:18000`，与板子无关 |

**转折点**：第 2 步。管道里的 `exit code 0` 是最容易骗人的信号；真正的判据是证据文件，不是进程退出码。

**弯路**：第一反应是"把临时文件改到 `build-temp/` 下、或者每 40 个分批删"。立刻否掉——只要还有按块删除，阈值迟早会到；而且分批删会引入新的状态管理。正确方向是**让删除次数恒为 0**，而不是想办法少删。

## 5. 根因

传输层把"每块一个临时文件、写完即删"当成无害的清理动作，但宿主环境对单轮内的文件删除次数有硬阈值（50）。长任务把这个"无害动作"放大成 512 次，必然在第 50 次被拦。这是**宿主策略与长时任务的交互**，不是 NOR 协议、固件或 SWD 的问题。

## 6. 修复

- `stages/board-lab/host/nor_restore.py::SwdLink.put_data()`：改成每次运行只创建 **一个** `blk-<tag>-scratch.bin`，每块覆盖写，不再 `unlink()`；同时去掉 `if tmp.exists(): raise`（否则第二块就会自锁）。文件只有 32 KiB，留在证据目录里当作传输草稿，注释写明它不是证据。
- 驱动里 `grep unlink|remove|rmtree` 现在**零命中**；`finalize()` 用的是 `os.replace`（重命名，不是删除），结束时才执行一次。
- 备选方案与放弃原因：把 scratch 放到 `build-temp/` 或按批删除。放弃，理由见上；另外放别处会让"证据自包含"变差，换电脑复核时还得带一个外部临时路径。

## 8. 学到的东西

1. 管道 `cmd | tee log` 的退出码是 `tee` 的。长任务的成功判据必须是**它自己写的证据文件**，不是 shell 的 exit code。
2. 长时任务里任何"每次循环做一次"的副作用都要按总次数重新评估：512 次删除、512 次网络调用、512 次弹窗，都会被宿主策略放大。
3. 宿主安全守卫拦的是动作类别，不是"删得对不对"；绕它的正确方式是取消动作，不是伪装动作。
4. 中断后先查证据完整性，再猜硬件故障——这次板子和固件全程没出错。

## 9. 简历表述

> 排查长时烧录演练在 49/512 中断的问题：定位到宿主批量删除守卫与"每块删临时文件"的交互，把传输层改为全程复用单个草稿文件、零删除，并用真机短程验证恢复流程不受影响；同时确立以证据文件而非进程退出码作为长任务验收判据。

## 10. 边界与未解决

- 该守卫是宿主环境策略，换机器/换设置后阈值可能不同；零删除的写法在任何情况下都更安全，但仍未在其他环境验证。
- 证据目录会累积约 7000 个小文件（每块多次 CLI 日志 + 头快照），磁盘占用未实测，后续可考虑压缩归档。
- 512 块全程重跑进行中；跑完还需 `build-temp/drill_accept.py` 验收 `manifest.json` 与 512 条事件的无缝覆盖。
- 上一次中断的 49 块是**幂等写入**（数据来自金标，芯片本来就等于金标），所以板子内容没有被破坏，但那次运行本身不构成证据。
