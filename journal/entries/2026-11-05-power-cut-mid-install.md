# 安装中途断电：旧 App 擦到一半拔电，板子自己装完还带着正确凭证

- 日期：2026-11-05
- 类型：验证（实机）/ 缺陷（工具侧三次事故）
- 关键词：`power-cut` `install-window` `secure-boot` `ticket` `swd` `pyserial`
- 验证等级：实机（主机侧脚本与证据文档同步更新）

## 1. 一句话

把断电点从"下载中"推进到"安装中"——`11 01` 复位后 loader 正擦内部 960 KiB
App 槽的第 3~4 秒拔掉全部供电，重新上电后板子**自己重做安装**，终态
`IDLE / application / v19 / 44824 B / seq 162`，且 SWD 读回逐字节等于构建产物、
96 B 凭证签名等于断电时正在装的 v19 包签名。

## 2. 背景与约束

这是断电实验的最后一块实机空白：下载中断（9690 B 处拔电）已验证，但安装窗口
（旧 App 被擦、新镜像写一半、凭证未写）只有主机模型 429 个切点覆盖，从未上过
真板。约束：不改任何 C 代码（恢复逻辑早在 `boot.c` 里，只欠验证）；窗口约 8 s，
操作者需要在正确瞬间拔线；CRLF 源码、纯 ASCII 命令行。

## 3. 现象

`power_cut_upgrade.py --cut-phase install`（本轮新增模式）：`34` 14.25 s →
89 帧 `36` → `37 → 77`（v19 验签，状态落 READY）→ `11 01` → 原始串口监视，
banner 出现 `loader: selecting boot target` 判定窗口开启 → 每秒打印
`PULL NOW`。第 3 s 提示打出后串口句柄死亡（第 4 s 未出现）→ 三路供电已拔。
~40 s 后插回：板子无人干预，终态 `IDLE / application / v19 / 44824 B / seq 162`，
内部 44824 B 与构建产物逐字节相同（sha256 `47f604c1…`），凭证签名
`2e93f593…` == v19 包尾部签名。

## 4. 排查过程

| 步骤 | 我怀疑什么 | 做了什么 | 结果 |
|---|---|---|---|
| 1 | 重启实验失败：COM9 拒绝访问 | 等 6 s 重试 + .NET SerialPort 试开 | 句柄瞬时残留，端口实际空闲，重试即可 |
| 2 | 第一次窗口错过（30 s 无操作） | 读后台终端输出 | `PULL NOW` 只打在后台终端，操作者在聊天界面根本看不到 |
| 3 | 第二次断电后脚本退出码非 0 | 读 stderr | **断电检测成功后脚本崩溃**：句柄已死，恢复 `ser.timeout` 触发端口重配置抛 `PermissionError(13)` |
| 4 | 恢复取证：横幅 0 字节、status 超时、SWD `Data read failed` | 对照时间线 | 取证撞上板子的静默自愈安装：冷启动横幅在端口打开前已打完，loader 忙于安装不回 UDS |
| 5 | 判决"NOT the expected state"？ | 修脚本（重试/延长静默窗）后收"稳定态"二轮证据 | RECOVERED：状态、逐字节、凭证、横幅链全部齐 |

**转折点**：第 4 步意识到"第一轮取证的失败可能只是板子在忙"——板子行为没错，
错的是取证时机。断电判决不能只收事件瞬间一轮，要补稳定态一轮。

## 5. 根因

工具侧三次事故，机制各不相同：

1. **错过窗口**：拔电信号只存在于操作者看不到的输出通道（后台终端 vs 聊天窗口）。
2. **断电后崩溃**：pyserial 的 `ser.timeout = x` 会调用 `_reconfigure_port()`，
   设备消失后句柄失效，重配置直接抛 `PermissionError`——断电检测成功反而触发。
3. **取证失败**：恢复瞬间目标正处于自愈安装（设计如此），主机把它当成"没响应"。

## 6. 修复

- 文件：`stages/board-lab/host/power_cut_upgrade.py`
  - 新增 `--cut-phase install`：完整下载 + `37` + `11 01` 后监视原始串口，
    以 `selecting boot target` 判定窗口开启；`37` 期间传输层失败按断电分类
    （NRC 才是拒绝）；超时恢复包进 try/except。
- 文件：`stages/board-lab/host/power_cut_recover.py`（新增）
  - 等端口 → 横幅两轮（静默期 1 s→3 s，签名验证期间控制台静默 1–2 s，
    1 s 窗口恰好剪掉 `handing off` 行）→ status 读重试 5 次 → SWD 转储前
    等 3 s 且失败重试一次。
- 备选方案与放弃原因：把恢复取证并回 `power_cut_upgrade.py` 的 phase 4–6。
  放弃：崩溃已经证明一次脚本死亡会连带丢失全部证据，独立取证脚本与驱动脚本
  解耦，一个死另一个还能干活。

## 7. 验证

```
python host/power_cut_upgrade.py --port COM9 --cut-phase install --lead 15 \
    --image app_v19.img2 --out evidence/power-cut-install
python host/power_cut_recover.py --port COM9 --out evidence/power-cut-install-settled
```

| 项 | 期望 | 实际 |
|---|---|---|
| 断电点 | 安装窗口内 | 窗口第 3–4 s（3 s 提示打出，4 s 未出现） |
| 恢复终态 | role=application，v19 | `IDLE / application / v19 / 44824 B / seq 162` |
| 内部镜像 | == 构建产物 | 44824 B 逐字节相同，sha256 `47f604c1…` |
| 凭证 | 在位且属于 v19 | 96 B；签名 == v19 包签名 `2e93f593…`；头 v19/44824/crc D6B888DB/flags 1 |
| 恢复横幅链 | loader→App | `selecting boot target` → `handing off to the app at 08010000` → App 横幅 |
| 复位后可再升级 | — | 未在本轮测（v19 为终态；同板此前的闭环已证） |

未验证：断电瞬间电压采样（判据是串口句柄死亡 + 时间线）；断电后第一次冷启动
横幅（端口打开前已打完，读到 0 字节——板子静默自愈）。

## 8. 学到的东西

1. **恢复证据要收两轮**：事件瞬间一轮、稳定态一轮。第一轮的"超时/Data read
   failed/0 字节"可能只是目标在忙自愈，不是故障。
2. **pyserial 在设备消失后，任何对句柄的再配置（哪怕只是设 timeout）都会抛**；
   断电处理代码路径必须全部 try/except，否则"检测成功"变成"证据丢失"。
3. **人机协同的实验，信号通道必须直达操作者**：打在后台终端的 `PULL NOW`
   等于没打；改为聊天窗口实时发信号后一次成功。
4. 意外收获：错过窗口的第一次运行留下了**未打断的完整安装窗口 UART 序列**
   （`selecting` → `handing off` → App 横幅，1043 B），成了本实验的对照组。

## 9. 简历表述

> 在 STM32F407 OTA 平台上完成安装窗口断电实机验证：在 Bootloader 擦除内部
> App Flash 的第 3~4 秒切断全部供电，重新上电后设备无人工干预自愈——重做安装
> 并以 Ed25519 凭证（SWD 逐字节读回比对、签名与升级包交叉验证）运行断电时
> 正在安装的固件版本。

> 难点：8 秒窗口的人机协同触发、三次工具侧事故（信号通道不可达 / 断电检测后
> 句柄重配置崩溃 / 取证撞上静默自愈）的定位与修复。

## 10. 边界与未解决

- 无电压采样：断电判据是串口句柄死亡 + 主机时间线，不是 0 V 实测。
- 第一次冷启动横幅未捕获（0 字节），恢复链由显式复位后的完整横幅补证。
- 板载电源开关是否控制电轨仍是 unknown（本轮是拔线）。
- 安装窗口的更早切点（备份写入期间、READY 未落 INSTALLING 时）未单独采样，
  代码路径与本次同分支但切点不同。
