# 真实 CAN 完整 OTA 首次接线：A/B 对照把固件摘干净，卡点回到供电

## 1. 一句话

2026-11-09 晚第一次按 runbook 接线执行真实 CAN 完整 OTA，链路没建起来；用「烧回 11-07 打通时那一份镜像」的 A/B 对照，一次性排除了固件、构建变体、门控和 PC 脚本，把嫌疑收敛回板级供电与 `USB_232`。

## 2. 背景

11-07 真实 CAN 只读诊断已实机打通（PCAN-USB 500 kbit/s、ISO-TP 多帧 VIN 20 B）。11-09 白天完成不依赖硬件的准备：构建出可写 CAN loader/app、修正评估文档、写 `REAL_CAN_OTA_RUNBOOK.md`。用户说「三根线都接了」，于是开始第 41 号任务（烧基线 + 跑完整 OTA）。

## 3. 现象

- `PCAN-USB` OK、`STM32 STLink` OK，但 **CH340 三个历史实例全部 `Present=False`**，当前 COM4/5/6/7/10/11 全是蓝牙虚拟串口。
- ST-Link 目标电压 **2.87–2.88 V**；11-07 打通时是 **3.24 V**。这个 2.87 V 还恰好是 11-05 空闲态断电实验里「塌陷瞬间最后读数」。
- `CAN_Initialize=0x0`、`CAN_Write=0x0`、50 帧有回显、0 错误帧、`CAN_GetStatus=0x0`，但 `0x7E8` 回帧 **0**。
- 45 s 观察窗口每 5 s 发一次 `22 F190`，9 次全 0 响应。
- `uds_tool.py status --backend can` 直接 `CAN/ISO-TP response timeout`。

## 4. 排查（留弯路）

1. 先怀疑**新构建的可写 loader 烧成了 UART 诊断**：查二进制字符串，`CAN: normal physical 500 kbit/s` 与 `loader diagnostics: request 7E0, response 7E8` 都在、UART 字符串缺席 → 排除。
2. 怀疑 ST-Link 多次连接把内核按在 halt、或软件复位没生效：单独发 `-c port=SWD mode=normal -rst`，复测仍 0 回帧 → 排除。
3. 中途差点又拿 `CAN_GetStatus=0x0` 当「有节点在 ACK 的证据」，**当场自我更正**：这台兼容适配器不上报 ACK 错误，11-07 排障实录已经写过，0x0 只说明控制器自身没报错，不证明总线上有人应答。
4. 试着用 SWD 热读运行态寄存器：读到 `RCC_CR=0x03007083`（PLL 已锁）、bxCAN1 却是复位默认值（`SLEEP=1`、`BTR=0x01230000`、`IER=0`）、SysTick VAL 两次都 0。这些看起来像「时钟配过但 CAN 没初始化」，但 11-07 已经证明 **hotplug 快照是 halt/复位瞬间的假象**，所以只留档、不当结论。
5. 走 **A/B 对照**：把 11-07 打通时用过的 `diagnostics_READONLY_backup.bin`（sha256 `8a383388…`）整片擦除、烧回、校验、复位，用同一套脚本复测 → **仍然 0 回帧**。至此固件、构建、门控、PC 客户端全部摘干净。
6. 再走 **主动发帧探针**（11-07 翻盘那一招）：临时固件每 250 ms 主动发 `0x7E8`，载荷带运行时 `AFRH/BTR/MCR`，并用 `g_probe_stage` 标记跑到第几步。11-07 同一手法 8 s 收到 18 帧，这次 **0 帧**。`g_probe_stage` 读到 `0x1FFF2A4D`（不是 1–7），再次印证 SWD 读数不可信。

## 5. 根因

**本轮未定位到根因，只定位到边界。** 已确证的是「板子这一刻没有作为 CAN 节点工作」，且与 11-07 通过状态的**可量化差异**只有两处：CH340 不在线、ST-Link 目标电压 2.87 V（vs 3.24 V）。

最可能的解释（`leading hypothesis`，**推断，未实测**）：`USB_232` 那根线实际没插好 → 板子 5 V 轨没建立 → CAN 收发器不工作；ST-Link 读到的 2.87 V 是弱/寄生供电的表现。CAN 收发器需要 5 V，而 3.3 V 域有电并不能反推 5 V 有电——这正是 11-07 已经踩过一次的归因错误，这次不重犯。

## 6. 修复

本轮没有代码修复。做了三件保护性动作：

1. **恢复被探针覆盖的已提交证据**：本轮 `can_gate_probe.py` / `can_uds_acceptance.py` 失败运行会把 `nrc_72_gate_evidence.json` 和 `uds_readonly_acceptance.json` 从 `passed` 覆写成 `failed`。已 `git checkout` 还原，确认 `status=passed` 回来了。
2. **本轮失败结果单独留证**：新建 `evidence/can/bringup_20261109_ab.json`，`status=blocked`，与 11-07 的通过证据并存、互不覆盖。
3. **完整回滚**：探针源码残留 0、MDK 工程恢复 `--uart` 版、diagnostics bin 恢复 `8a383388…`、三份 GNU 构建记录 `git checkout` 还原、板子烧回原版只读固件并校验。两仓库工作树干净。

## 7. 验证

- 实测项：设备枚举、2.87/2.88 V 电压、Flash 备份各 64 KiB、可写 loader 全片擦除+写入+校验+复位、镜像字符串比对、50 帧底层探针、45 s 观察窗口、A/B 重烧对照、主动发帧探针、SWD 寄存器快照。
- **未实测**：板子 5 V 轨、CANH/CANL/GND 接线电阻与电平、P5 跳线目视、`USB_232` 物理连接。
- **未完成**：`0x34…0x37` → 安装 的完整 OTA，一次都没跑（连 `status` 都超时，不会盲目 flash）。

## 8. 学到

- **A/B 对照要烧「当时通过的那一份镜像」，不要只回滚源码**：源码相同不等于产物相同，这次直接比对 sha256 才算把固件摘干净。
- **失败探针会污染已提交的证据 JSON**：任何会写 `evidence/` 的脚本，在实验态跑之前要么改输出路径、要么先备份；否则「历史通过证据」会被一次失败无声降级。
- **`CAN_GetStatus=0x0` 与 `bus.state=ACTIVE` 都不是 ACK 证据**；这台兼容适配器不上报 ACK 错误，11-07 的教训不能在下一轮换个别名又犯一次。
- **电压读数可以做 A/B**：3.24 V（通过）vs 2.87 V（不通）是比「灯亮不亮」硬得多的线索，但仍只是供电线索，不是根因。
