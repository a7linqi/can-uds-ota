# 512 块演练在第 478 块停住——但芯片内容和金标一致

- 日期：2026-11-04
- 类型：缺陷
- 关键词：`nor-restore` `swd-mailbox` `race` `crc32`
- 验证等级：实机

## 1. 一句话

整片恢复演练跑到 477/512 块时主机报 `status 0x3`（上一块的 BLOCK_OK）而停住；
用独立只读核验确认**器件自算整片 CRC = `0xA4188821`，等于金标**——
数据没坏，坏的是握手协议。

## 2. 背景与约束

演练 22:01 起跑，计划 512 块 × 32 KiB。期间不碰 SWD（会打断），
只在主机侧做别的活。跑完预期 23:26。

## 3. 现象

23:20:37 演练自己结束，`manifest.json`：

```json
{"status":"failed","mode":"restore","hardware_mode":true,
 "error":"device did not take the command at block 478 submit (status 0x3)"}
```

- `events.jsonl` 干净地停在 477 条，`offset` 无缝铺到 15 597 568（14.91 MiB）；
- 最后三条耗时在变长：11.125 s → 11.75 s → 14.031 s。

CLI 记录显示第 478 块的头部**全部写进去了**，而且返回码都是 0：

```
-w32 0x200003bc 0x1de      seq=478
-w32 0x200003c0 0xee8000   offset
-w32 0x200003c4 0x8000     length
-w32 0x200003d0 0xf4f47777 crc32
-w32 0x200003d4 0x1de      ack=478   ← 门铃
-u   0x200003b0 0x28       ← 0.73 s 后读，status 仍是 0x3
```

## 4. 排查过程

| 步骤 | 我怀疑什么 | 做了什么 | 结果 |
|---|---|---|---|
| 1 | 芯片被写坏 | 解 477 条事件的 `crc32` 与金标逐块比对 | 已写的块全部逐块一致 |
| 2 | 固件崩了 | 直接解码邮箱 40 字节（`hdr-*.bin`），看 status/error | `status=0x3`、`error=0`，**没有错误码**，说明不是拒绝，是没消费 |
| 3 | 剩下的 35 块是脏的 | 跑 `--mode verify`（只读，69 s） | 器件自算整片 CRC **`0xA4188821`** = 金标 → **整片内容正确** |
| 4 | verify 为什么也报 failed | 读它的 DONE 头 | `offset=0x0`，期望 `0x1000000`；但 `crc32=0xA4188821`、`error=0` |
| 5 | 是不是固件版本旧了 | 比 `nor_restore.c`(15:58) 与 `.bin`(21:45) 时间戳 | 不是，二进制比源码新 |
| 6 | 那为什么同一固件两次对一次错 | 翻 21:48 / 21:58 两次历史 verify 的 DONE 头 | 两次都是 `offset=0x1000000`；**只有 23:22 这次是 0** |

**转折点**：第 6 步。同一份固件、同一个校验，两次对一次错 → 不是构建差异，
只能是**读到了半写状态的头部**。

## 5. 根因（分两层，可信度不同）

**已证实（第 2 层）**：邮箱头是 40 字节，主机一次 `-u` 批量读出，**没有防撕裂机制**。
器件在 `NR_S_FINAL_CRC` 里依次写 `offset=total`、`length=0`、`crc32`、`ack=0`，
最后才 `publish_status(DONE)`。地址上 `offset`(0x10) 在 `status`(0x18) 之前，
批量读按地址递增，**完全可能先读到旧 offset、后读到新 status**，得到一个
"状态已完成但偏移为 0"的不可能组合。第 4 步拿到的正是这个组合。

**未证实（第 1 层，块 478 停住）**：`NR_S_COMMIT` 无条件执行 `mb->h.ack = 0u;`。
如果主机在器件仍处于 COMMIT 时写入门铃，这个写会被这一句清掉，
之后 READY 永远等不到 `ack == seq+1`，而 STATUS 停留在刚发布的 `BLOCK_OK`——
与第 2 步观察到的 `status=0x3 / error=0` 完全吻合。
**但这一步还没有被直接观测到**：没抓到"门铃写入发生在 COMMIT 之内"的时序证据。

## 6. 修复（仅第 2 层，第 1 层待定）

- 待办 A（主机侧，防撕裂读）：读头部后**再读一次**，两次的 `magic/seq/offset/status`
  完全相同时才采信；或加一个器件侧递增的 `tick` 做 seqlock。
- 待办 B（固件侧，门铃保护）：`NR_S_COMMIT` 里只在
  `mb->h.ack == c->seq` 时才清 0，避免清掉"下一块"的门铃。
- 备选方案与放弃原因：直接给主机加重试（再写一次 ack）。
  放弃原因：重试能绕过症状，但会掩盖"门铃被丢"这个设计缺陷，
  而且在真实 OTA 场景下丢门铃等于丢一次升级请求，不能靠重试兜。

## 7. 验证

| 项 | 期望 | 实际 |
|---|---|---|
| 512 块跑完 | 512/512 | **477/512 后停住** |
| 芯片整片 CRC | `0xA4188821` | **`0xA4188821`（器件自算）** |
| 已写 477 块逐块 CRC（`zlib.crc32(img[off:off+len])` 对比事件里的 `crc32`） | 0 处不一致 | **0 处不一致**（477 条全对） |
| 未触及区间 | — | `0xEE8000..0xFFFFFF` 共 **1 146 880 字节 / 35 块**没有写 |
| 只读核验 | `status=passed` | `failed: DONE offset 0x0 != total 0x1000000` |
| 历史同样核验（21:48 / 21:58） | `offset=0x1000000` | 两次都对 |

未验证：块 478 停住的直接原因（门铃被 COMMIT 清掉）**没有拿到时序证据**，
只是与观察现象一致的最简解释。要证实需要在固件里加计数（被清掉的 ack 次数）后复现。

## 8. 学到的东西

1. **"失败"要先分清是数据失败还是协议失败。** 这次数据是完好的（器件自己算的 CRC 就是金标），
   坏的是握手。如果不先测芯片就去重跑，会白白再花 80 分钟。
2. **同一个固件两次对一次错，就是竞态。** 不要先怀疑版本、配置、线材。
3. 40 字节结构体跨进程读，天然不是原子的。凡是有"状态位 + 数据"的共享内存，
   都要么双读校验，要么用序号锁。

## 9. 简历表述

> 定位 NOR 整片恢复演练在 477/512 块的可复现性故障：先用器件自算 CRC 证明数据无损、
> 排除"写坏芯片"，再从"同一固件两次成功一次失败"判定为共享内存握手竞态，
> 指出 40 字节邮箱头缺少防撕裂机制。

## 10. 边界与后续

- 演练**没有通过**。512/512 从未完成过，目前最好成绩是 477/512 + 整片 CRC 正确。
- 板子当前跑的是还原固件且已进入 DONE 停留态，要再次实验必须先复位并重烧。
- `drill_accept.py` 对这次运行的判定是 `FAILED (6 problem(s))`，判定本身正确。
