# 修掉 0x22 用 0x72 顶替"响应过长"的 NRC 错误

- 日期：2026-11-04
- 类型：缺陷
- 关键词：`uds` `nrc` `iso14229-1` `0x22` `buffer`
- 验证等级：主机模型

## 1. 一句话

`ReadDataByIdentifier` 的响应放不进缓冲区时，ECU 回的是 `0x72 generalProgrammingFailure`，
而 ISO 14229-1 要求 `0x14 responseTooLong`；顺手发现一条测试"因为错误的原因而通过"。

## 2. 背景与约束

上一轮做完 ISO-TP 的 reserved STmin，代码体检清单里还剩一条没扫：
`uds.c` 的 DID 拼接边界。约束照旧：不改产品仓库，只在 `build-temp/` 里取证；
数字只用当场实测；不碰板子（NOR 512 块演练在跑，SWD 被占）。

## 3. 现象

`append_did()` 用三个负返回码区分失败：`-1` DID 不支持、`-2` 缓冲区放不下、`-3` 元数据读失败。
`handle_read_data()` 把后两个合并：

```c
if (r == -2 || r == -3) {
    return nrc_reply(resp, max, 0x22u, NRC_GENERAL_PROGRAMMING_FAILURE);
}
```

拿 `22 F1 90`（VIN，数据 17 字节，响应共 1+2+17=20 字节）打一个 19 字节的缓冲区：

```
resp_max=19 -> 7F 22 72
```

`22 02 00`（`0x0200`，40 字节）打 42 字节缓冲区（需要 43）：同样 `7F 22 72`。

## 4. 排查过程

| 步骤 | 我怀疑什么 | 做了什么 | 结果 |
|---|---|---|---|
| 1 | 响应构建器会越界 | 写带哨兵的探针（缓冲区前后各 64 字节 `0xA5`），直接调 `uds_handle()` | 12146 条检查 0 次越界；失败只有 NRC 值不对那几条 |
| 2 | 是不是我的夹具写错了 | 检查 `0x22` 长度奇偶那组 | 是：填充字节 `00 00` 成了不支持的 DID，改夹具后失败从 5 降到 1 |
| 3 | 规范到底是 0x14 还是 0x72 | 查 ISO 14229-1 的 `$22` supported NRC 表 | 明确写着 0x14 用于"响应超出传输层上限，例如一次请求多个 DID" |
| 4 | 补丁会不会打破现有测试 | 四组合构建（原版/补丁 × 原版测试/补丁测试） | 只打补丁时 `test_uds.c:194` 变红 |
| 5 | 那条测试为什么红 | 读它传的参数 | `resp_max=42`，`0x0200` 需要 43，**它走的就是"放不下"分支**，却断言 0x72 |

**转折点**：第 5 步。`B.eeprom.read_fail_after=-1;` 就在调用上一行 —— EEPROM 读是成功的，
根本到不了 `-3`。这条测试从写下的那天起就在测"响应过长"，只是旧代码把两个原因
映射成同一个 NRC，所以它一直绿着，还顺手把错误行为钉成了契约。

## 5. 根因

两个语义完全不同的失败原因共用了一个返回码分支。因为 `-2`（容量问题，tester 可以拆包重试）
和 `-3`（存储故障，ECU 真出问题了）被压成同一个 `0x72`，对外无法区分，
诊断方向会被误导到"ECU 内部故障"而不是"这条响应发不出去"。

## 6. 修复

- 文件：`src/core/uds.c`
  - 新增 `#define NRC_RESPONSE_TOO_LONG 0x14u`
  - 把 `if (r == -2 || r == -3)` 拆成两个分支
- 文件：`tests/test_uds.c`
  - 42 字节那条断言改成 `0x14`
  - **补一条**：同样的请求给 43 字节必须返回 43 字节的肯定响应 —— 证明判据是缓冲区大小，
    不是数据本身坏了
- 备选方案与放弃原因：改 `append_did()`
  在放不下时截断返回已拼接的部分 DID。放弃原因：ISO 14229-1 允许厂商限制一次请求的 DID 数
  （超了报 0x13），但"发一半"会让 tester 拿到结构不完整的响应，解析更糟。
  保持全或无，只把否定码改对。

## 8. 学到的东西

1. **两个失败原因共用一个错误码，测试就再也测不出它们。** 这条断言一直绿着，
   因为它断言的那个值把两条路径都覆盖了 —— 覆盖率高不代表覆盖对。
2. **"测试挂了"先看测试传了什么参数。** `resp_max=42` 和"需要 43 字节"摆在一起，
   一眼就能看出它没在测自己声称的东西。
3. 同一个模式在本项目出现了两次（`test_protocol_edges.c:82` 把 reserved STmin 的中止行为
   写成断言）。凡是"补丁一改，测试就红"的地方，都值得先问一句：它是不是把 bug 当成契约了。

## 9. 简历表述

> 审计 UDS 诊断服务端实现，发现 `ReadDataByIdentifier` 在响应超长时返回错误的否定响应码
> （0x72 应为 0x14），修正后补齐带哨兵缓冲区的边界测试（4067 次调用零越界），
> 并用四组合构建证明修复与测试互相判别（3164/0 → 3174/0）。

> 识别出一条"因错误的原因而通过"的历史测试：它传入的缓冲区比响应小一字节，
> 实际走的是容量分支，却断言了存储故障的响应码。
