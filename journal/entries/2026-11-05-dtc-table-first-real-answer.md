# 让 DTC 表第一次从真实板子上答话

- 日期：2026-11-05
- 类型：功能（实机验证）
- 关键词：`uds` `dtc` `0x19` `0x14` `nrc` `board-lab`
- 验证等级：主机模型（此前）/ 实机（本次，UART 台架链路）

## 1. 一句话

`0x19` / `0x14` 写完后只在主机模型里被断言过，这次让它在真实 UART 链路上跑一遍：制造一个真实失败、读回来、清掉、再读空。

## 2. 背景与约束

DTC 表是 2026-11-05 加的（RAM 8 条，四类码，掉电清空）。当时的验收只有主机模型断言：注入失败路径 → 检查 `dtc_count` 和掩码过滤。

主机模型能证明"逻辑对"，证明不了三件事：**固件里这张表存在**、**UDS 分发真的把 `0x19` 路由到了它**、**板子回的状态字节与规范一致**。

约束：用户不在现场，只能远程操作。所以这条验证必须做到不写 Flash、不改元数据状态机、不依赖任何物理动作（不按键、不拔插、不断电）。三条都满足，才能在这一轮做。

## 3. 现象

改造前：`0x19` 在任何链路上都没有返回过真实字节。文档里写的是"未在真实 CAN/UART 链路上跑过"。

实测输出（COM9 / 115200，板子在 v13 应用态，IDLE）：

```
22 02 00               -> 62 02 00 01 01 ... 80         (状态 DID，44 字节记录)
19                     -> 0x13                            (长度错)
19 03 FF               -> 0x12                            (子功能不支持)
14 FF FF               -> 0x13                            (groupOfDTC 是 3 字节)
14 00 00 00            -> 0x31                            (只支持 FF FF FF)
19 02 FF               -> 59 02 2B                        (空表)
19 01 08               -> 59 01 2B 01 00 00               (count=0)
27 01                  -> 67 01 5E E9 79 B1
27 02 BB5A7BC9 (wrong) -> 0x35
27 01                  -> 67 01 FC B0 F3 62
27 02 D71D229A (wrong) -> 0x35
27 01                  -> 67 01 1A 78 6D 13
27 02 72E42AE7 (wrong) -> 0x36                            (第 3 次：记 DTC 并锁定)
19 02 FF               -> 59 02 2B 2B C1 04 00            (0xC10400, status 0x2B)
19 01 08               -> 59 01 2B 01 00 01               (count=1)
14 FF FF FF            -> 54
19 02 FF               -> 59 02 2B                        (空)
19 01 08               -> 59 01 2B 01 00 00               (count=0)
```

`0x2B` = `TEST_FAILED(0x01) | TEST_FAILED_THIS_CYCLE(0x02) | CONFIRMED(0x08) | TEST_FAILED_SINCE_CLEAR(0x20)`，与 `uds_dtc_record()` 写入的 `UDS_DTC_STATUS_AVAILABILITY` 一致。

## 4. 排查过程

| 步骤 | 我怀疑什么 | 做了什么 | 结果 |
|---|---|---|---|
| 1 | DTC 代码在工程里 | 在 `D:\Project\Can\ota-core` 全量 grep `dtc` | **零命中**，连 `0x19` 都没有 |
| 2 | 也许根本没实现，文档吹了 | 去看另一个目录 `D:\Project\Can-learning` | `uds.c` / `uds.h` 里齐全 |
| 3 | 两份 `ota-core` 谁是真的 | 比对 `src`、`include` 目录 | **12 个 src + 14 个 include 不同**，且 `Can-learning` 多一个 `can_uart.c` |
| 4 | 那实机固件是哪份构建的 | 查 `i2c_bus_clear` 在哪份里 | 只在 `Can-learning`；`Can` 的 BSP 没有 → 活代码在 `Can-learning` |
| 5 | 怎么在不写 Flash 的前提下造一个真实 DTC | 读 `handle_security()` | 连续 3 次错 key 就走 `uds_dtc_record(UDS_DTC_SECURITY)`，全程不碰存储 |

**转折点**：第 4 步。`i2c_bus_clear` 是 2026-11-05 现场修好的、救回板子的代码，它只在 `Can-learning` 里，而 `Can/ota-core` 没有 —— 这说明 `Can` 里的 `ota-core` 是**旧快照**，不是可构建的工程。第 1 步的"零命中"不是功能缺失，是我在错误的树上找。

## 5. 根因

DTC 功能本身没有缺陷。缺的是**一次真实链路的验收**；而这轮真正的发现是另一个东西：`D:\Project\Can` 与 `D:\Project\Can-learning` 各有一份 `ota-core`，**已经分叉**（12 个源文件、14 个头文件不同）。`Can` 那份停留在 i2c 修复之前，如果照着它构建，会得到一个"看似正常、但会在 EEPROM 写中途被复位后永久卡在 loader"的固件——正是 2026-11-05 现场修掉的那个缺陷。

## 6. 修复

- 文件：`stages/board-lab/host/uds_dtc_probe.py`（新增）
  - 只用 `0x19` / `0x14` / `0x27`，不写 Flash、不改元数据、不发送 `10 02`（不触发 `boot_request` 落盘）。
  - 每个边界用例比对**精确 NRC**（`0x13` / `0x12` / `0x31`），不是"有报错就算过"。
  - 处理了"服务器已经被锁着"的情况：`27 01` 若回 `0x36`（锁定 10 秒窗口内），等 11 秒再取 seed，避免把"上一轮留下的锁"误判成本轮失败。
  - 复用 `uds_stage_d.calc_key`，不自己再写一遍 key 算法（此前手写 XOR 版本在板子上回 `0x35`，把测试失败伪装成服务器拒绝）。
- 备选方案与放弃原因：本可以顺便验"包校验 DTC（`0xC10200`）"，但那要走 `0x34` → 擦 1 MiB 槽 → 传坏包 → `0x37`，代价是约 20 秒真实擦写并让元数据停在 `DOWNLOADING`。这轮先不引入状态变更，只做零副作用的那一条。
- 备选方案二：也可以验"外部 NOR DTC（`0xC10100`）"和"元数据 DTC（`0xC10300`）"，但两者都需要真实的硬件故障（总线打不开 / EEPROM 读失败），远程制造不了。

## 7. 验证

```
python stages/board-lab/host/uds_dtc_probe.py --port COM9 --out stages/board-lab/evidence/uds-dtc
```

| 项 | 期望 | 实际 |
|---|---|---|
| `19`（2 字节） | NRC `0x13` | `0x13` |
| `19 03 FF` | NRC `0x12` | `0x12` |
| `14 FF FF`（3 字节） | NRC `0x13` | `0x13` |
| `14 00 00 00` | NRC `0x31` | `0x31` |
| 基线 `19 02 FF` | 3 字节空表 | `59 02 2B` |
| 3 次错 key | `0x35` `0x35` `0x36` | 一致 |
| 失败后 `19 02 FF` | 含 `0xC10400`，status `0x2B` | `59 02 2B 2B C1 04 00` |
| 失败后 `19 01 08` | count 1 | `01` |
| `14 FF FF FF` | `54` | `54` |
| 清后 `19 02 FF` / `19 01 08` | 空表 / count 0 | `59 02 2B` / `00 00` |

脚本自身判定：`boundary_all_ok` / `security_dtc_recorded` / `count_went_up` / `clear_answered_0x54` / `table_empty_after_clear` 五项全 `true`，`passed: true`。

未验证：`0xC10100`（外部 NOR）、`0xC10200`（包校验）、`0xC10300`（元数据）三条码在实机上从未被触发过——前两条要真实擦写失败，第三条要 EEPROM 读失败。另外这张表掉电清空的语义也没有实测（要断电，用户不在现场）。

## 8. 学到的东西

1. **"在错误的目录里 grep 不到"会被误读成"功能没实现"**。当时第一反应是文档吹了，不是路径错了。先确认自己在哪棵树上，再怀疑代码。
2. 两份同名工程分叉，比"没有工程"更危险：它会安静地构建出一个缺少关键修复的固件，而构建过程一切正常。
3. 零副作用的实机验证是存在的，值得专门设计：`0x19`/`0x14`/`0x27` 组合能在不写一个字节 Flash 的情况下制造并观察到一条真实的失败记录。
4. 安全访问的锁定是 10 秒窗口，测试脚本必须能区分"我这次弄坏的"和"上次留下的"——否则会得到一个看起来很严重的假失败。

## 9. 简历表述

> 在 STM32F407 上用 UART/CAN 链路实测 UDS 诊断服务 `0x19`/`0x14`：设计零副作用验证方案（不写 Flash、不改状态机），制造真实安全访问失败并读回 `0xC10400`（status `0x2B`）、验证计数与清除语义，覆盖 4 条边界 NRC（`0x13`/`0x12`/`0x31`），5 项自动判定全部通过。

## 10. 边界与下一步

- 这只证明 `0xC10400` 一条路径。另外三条码仍只有主机模型证据。
- 板子在过程中被锁定过 10 秒（3 次错 key 的必然结果），之后自动解除；最终停在 v13 / IDLE，DTC 表已清空。
- 下一步候选：包校验 DTC（需要真实擦写，约 20 秒）、安全启动（App 启动前验签名）、硬件 IWDG。
