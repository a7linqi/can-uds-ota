# 把"串口一个字节都收不到"做成对照实验：BOOT0 / VTOR 判据

- 日期：2026-11-04
- 类型：缺陷（推翻自己的判断）
- 关键词：`boot0` `vtor` `dtr-rts` `pyserial` `stm32`
- 验证等级：**实机**（COM9 / 115200 / SWD 读 VTOR）

## 1. 一句话

早先"板载 CH340 与 PA9/PA10 没连通"的结论是错的：那时芯片根本不在我们的固件里，而在 ST 原厂系统 Bootloader 里，USART1 从未被配置。

## 2. 背景与约束

真机 UART 台架一开始完全无响应。当时的两条证据：
① 关掉 `RXNEIE` 后发 9 字节，`RXNE/ORE/FE` 全 0；② 复位瞬间抓串口 0 字节。
硬件与固件都没动过，最终却通了 —— 说明当时的测量条件有问题，必须把"为什么"钉死，否则以后还会误判。

## 3. 现象

同样的串口、同样的板子、同样的固件：一开始"完全没有字节"，后来"三个服务 20–30 ms 稳定回包"。

## 4. 排查过程

| 怀疑 | 做法 | 结果 |
|---|---|---|
| 线接错 / 没接 | 用 `-w32` 改 CR1 后发字节看 `RXNE` | 全 0 —— 当时据此误判"硬件没连通" |
| 板子没跑我们的固件 | 读 `VTOR`（0xE000ED08） | **`0x1FFF0000`** = 系统 Bootloader |
| 谁把板子送进 Bootloader | pyserial 打开端口时的 DTR/RTS | 默认 `DTR=1 RTS=1`，接在正点原子"一键下载"电路的 BOOT0/RESET 上 |

转折点：不再问"线通不通"，改问"**芯片此刻是不是在跑我们的固件**"。

## 5. 根因

打开串口 → DTR/RTS 被拉高 → BOOT0 在下次复位时为高 → 芯片进入 ST 系统 Bootloader →
USART1 完全不配置，PA9/PA10 无人驱动 → 收发都是 0 字节。

## 6. 修复

`tools/pc/transport.py`：打开端口后立即 `dtr=False; rts=False`；再等 0.4 s 让固件启动完、
清空输入缓冲。（同一批还修了"一次 read 丢多帧"，见 `2026-11-04-uart-bringup.md`。）

## 7. 验证（对照实验）

| 条件 | VTOR | 判定 |
|---|---|---|
| 端口未打开，SWD 复位 | `0x00000000` | 正常 app（复位值 0，向量表在 0x08000000） |
| **pyserial 默认打开端口（DTR=1 RTS=1）+ 复位** | **`0x1FFF0000`** | **系统 Bootloader** |
| 拉低 DTR/RTS 后再复位 | `0x00000000` | 回到 app |

固件用 `HAL_UART_Receive_IT` 逐字节收：中断关掉后收到一个字节 `RXNE` 就该保持 1，
读到 0 只能说明该字节从未到达 USART1 —— 与"Bootloader 里 USART1 未配置"完全吻合。

## 8. 学到的东西

1. 判断"通信不通"要先确认**对端是否在跑你以为的程序**，否则测的是另一个系统（这里是 ST Bootloader）。
2. 串口工具的默认电平是有副作用的：DTR/RTS 在开发板上常接复位/BOOT0，"打开端口"本身就是一次硬件动作。
3. 否定性结论（"没连通"）比肯定性结论更需要对照实验，因为它无法被一次成功反证。

## 9. 简历表述

「定位串口零响应的真因：pyserial 打开端口默认拉高 DTR/RTS，经开发板一键下载电路把 BOOT0 置高，MCU 复位后进入系统 Bootloader；用 VTOR（0x1FFF0000 vs 0）做判据建立对照实验，修复后真机 UDS 稳定回包。」

## 10. 边界与未解决

- 只在正点原子探索者 V3（一键下载电路）上验证；其他板子的 DTR/RTS 接线可能不同。
- 若用户刻意要用一键下载（烧程序），需要另行拉高 DTR/RTS，当前工具不支持该模式。
