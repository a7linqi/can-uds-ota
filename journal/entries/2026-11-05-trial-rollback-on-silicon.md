# TRIAL 回滚：让一块板子"升级失败"给你看

## 1. 一句话

造一个"能启动、能应答、就是拒绝确认自己"的 App，在实物上跑出了完整回滚：
三次启动机会用尽 → loader 从备份区还原上一版 → 读回内部 Flash 与升级前的镜像逐字节相同。

## 2. 背景

这个项目的核心卖点是"升级中断后仍能恢复"。到 2026-11-05 傍晚，
这句话的全部证据是主机模型里的 420 个断电场景和一串断言——**实物上一次都没回滚过**。

`boot.c` 里回滚路径写得很完整（`READY → INSTALLING → TRIAL → RESTORING`），
主机测试也覆盖了，但"代码里有"和"硅片上跑过"是两件事。

原本计划先用真实断电来做，但断电实验需要精确控制时机，当天不方便。
后来发现：**回滚根本不需要断电**。TRIAL 失败判定靠的是"启动次数"，而复位就够了。

## 3. 现象（预期行为）

设计预期：

1. 装一个坏版本 → 状态进 `TRIAL`
2. 它不确认自己 → 每次复位吃掉一次 `boot_attempts`
3. `boot_attempts >= MAX_BOOT_ATTEMPTS`（= 3）→ 回滚
4. 从备份区还原升级前的版本 → 状态回 `IDLE`，`pending` 清零

## 4. 排查：怎么造一个"必挂"的 App（三个方案，前两个被否）

**方案一：塞一个 HardFault 的镜像。**
问题：它连 UDS 都不应答，我全程看不到 `boot_attempts` 涨到几，实验变成黑盒。
而且"挂了"和"不确认"是两种不同的失败，混在一起说不清是验证了哪条路径。

**方案二：塞一个 `while(1)` 的镜像。**
同样的问题——能证明回滚，但证明不了"App 活着、只是不健康"这个更严格的情形。

**方案三（采用）：让它 `app_healthy()` 返回假。**
翻 `explorer_reference.c` 发现健康状态是个编译期常量：

```c
int ota_user_app_healthy(void) { return OTA_EXPLORER_BOOT_ROLE==2 ? 1 : 0; }
```

于是加一个只影响这一个返回值的开关 `OTA_EXPLORER_APP_SICK`，
造出来的 App 能完整启动、能应答状态 DID、能打印横幅，只是永远不调
`boot_accept_app_health()`。这样整个 trial 过程是**可观测**的。

顺便确认了一个容易搞错的点：`31 01 00 01` **不是**确认。
`uds.c` 里的注释写得很清楚——

> Routine 0001 verifies a READY package. Health confirmation belongs to the running app.

确认只能由运行中的 App 自己发起（`boot_accept_app_health()` → `boot_confirm()`），
诊断仪在跳转前没法替它确认。这个设计是对的：否则主机可以在 App 还没跑起来时就"确认"它健康。

## 5. 根因（这不是 bug，是补验证）

回滚能不能成，取决于 `backup_ok()` 是否认可备份区内容：

```c
h.version == m->active_version && h.image_size == m->active_size && ...
```

一开始我以为这里会失败——因为直觉上"备份的是上一版，而 active 已经是新版"。
读代码才发现：**TRIAL 期间 `active_version` 仍是旧版本**。
`boot_confirm()` 才会把 `pending_*` 提升成 `active_*`，而它要在 App 确认之后才发生。
所以 TRIAL 阶段"备份区 = active_version"是自洽的，回滚目标永远精确等于升级前那一版。

**验证方式本身值得记一笔**：读状态 DID 会关串口，而关串口 = 复位。
所以"每读一次状态"就顺带推进一次 trial 计数——实验的观测动作和驱动动作是同一个。

## 6. 修复（本次交付的是验证手段 + 一个测试开关）

- `platform/stm32f407/board/explorer_reference/explorer_reference.c`：
  加 `OTA_EXPLORER_APP_SICK`（默认 0，`#ifndef` 兜底），为真时 `ota_user_app_healthy()` 返回 0。
  注释里写死"never define it in an image that ships"。
- `build-temp/build_stage_d.py`：加 `sick` 变体（其余定义与 `app` 完全一致），并把该宏加入 `OWNED`。

产品代码零改动——回滚路径本来就是对的，缺的只是有人去跑它。

## 7. 验证（全部实机，2026-11-05）

起点：`active_version=11`，`IDLE`，`seq 87`，`role=application`。

装 `sick v12`（44480 B / `sha256 508ca8b8…`，签名包 44576 B），
走完整 `--handoff` 链：交棒 → `34` 13.86 s → `37` 验签 0.34 s → `31` 校验 0.28 s → 跳转。

然后推进 trial（每轮读状态即一次复位）：

| 轮次 | state | attempts | active | pending | seq |
|---|---|---|---|---|---|
| 0 | TRIAL | 2 | 11 | 12 | 95 |
| 1 | TRIAL | **3** | 11 | 12 | 96 |
| 2 | 无响应（正在回滚） | — | — | — | — |
| 3 | **IDLE** | **0** | **11** | **0** | 98 |
| 4–7 | IDLE | 0 | 11 | 0 | 98 |

第 2 轮的超时不是故障，是 loader 正在擦 960 KiB 内部 Flash 并重写；
第 3 轮回来时 `pending_version` 已清零、`boot_attempts` 归零、状态 `IDLE`。

**判决性验证**：用 ST-Link 读回 `0x08010000` 共 44288 B：

```
rollback   44288 B  sha256=bed181e9ea2b4089  crc32=0x5F966357
v11 ref    44288 B  sha256=bed181e9ea2b4089  crc32=0x5F966357
identical: True
```

回滚不是"大概回去了"，是**逐字节等价**于升级前的镜像。

**回滚后系统仍可用**：紧接着装正常的 v13（带 I2C 总线清除，44480 B / `sha256 2a0a7c20…`），
`34` 13.91 s、`37` 0.34 s、`31` 0.30 s，跳转成功，最终 `active_version=13`、`seq 106`、`IDLE`。
说明 `RESTORING` 之后元数据和备份区都处于干净状态，能继续升级。

## 8. 学到

- **"中断"和"失败"是两条不同的恢复路径。** 断电中断走的是"重做安装"；TRIAL 失败走的是"还原旧版"。
  前者我之前用主机模型测过，后者这次在硅片上验证了。两条加起来才叫"双保险"。
- **观测手段会影响被测对象。** 读状态会复位，复位推进 trial——这既是巧合也是设计好的耦合
  （loader 每次启动必然递增计数）。如果不理解这层，会把"读一次涨一次"误判成 bug。
- **测试开关要选语义最小的地方。** 改 `app_healthy()` 一个返回值，比塞一个 HardFault 镜像
  更能说清"我验证的是哪条路径"。
- **确认权归 App，不归诊断仪。** 这条从代码注释里读出来，比从规范里背下来更牢。

## 9. 简历表述

> 在 STM32F407 实物上验证固件回滚：构造"可启动但拒绝自我确认"的应用镜像触发 TRIAL 失败，
> 三次启动机会用尽后由 Bootloader 从外部 NOR 备份区自动还原上一版本，
> ST-Link 读回内部 Flash 与升级前镜像逐字节一致（CRC32 `0x5F966357`），回滚后系统可继续正常升级。

## 10. 边界

- **没有做真实断电中断。** 这次验证的是"App 不健康"路径，不是"写到一半掉电"。
  后者的证据仍只有主机模型的 420 个场景。
- **回滚耗时未单独测量。** 只知道它在一次读状态超时（15 s）之内完成，
  没有像 `0x31` 那样精确计时。
- `MAX_BOOT_ATTEMPTS=3` 是编译期常量，没有测试"改成 1 或 5"的行为。
- `sick` 变体只存在于 `build-temp` 的临时构建脚本里，不在产品构建矩阵中；
  如果以后要长期保留这条回归，应该把它做成正式的硬件测试用例而不是随手脚本。
- 备份区内容没有直接读出来核对（NOR 是外部 SPI，ST-Link 读不到，只能通过固件读）。
  这次是用"回滚后的内部镜像 == 升级前镜像"间接证明备份内容正确。
