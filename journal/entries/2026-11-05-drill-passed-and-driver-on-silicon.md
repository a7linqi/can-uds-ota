# 跑满 512 块恢复演练，并把产品 NOR 驱动第一次接到真实硅片

- 日期：2026-11-05
- 类型：功能
- 关键词：`nor` `restore` `spi` `w25q128` `stm32` `crc32` `evidence`
- 验证等级：实机（T1 全片恢复、T3 只读探测）；目标构建（四套 GNU 镜像、八个编译变体）；主机模型（3385 断言 × 两套容量）

## 1. 一句话

修复握手判定后，16 MiB 旧片恢复首次跑到 512/512 且器件 CRC 与本机金标一致；随后把 `src/driver/spi_nor.c` 接进 explorer BSP 上板，用"器件读到的 256 字节 CRC32 == 离线金标同段 CRC32"证明产品驱动真的读通了。

## 2. 背景与约束

- 卖点是"升级中断后可恢复"，前提是**能任意重写回已知状态**。整片恢复跑不通，后面写坏了没兜底，所以 T1 排在所有写入动作之前。
- 约束：不得重复读整片（一次 90 分钟，且要占用唯一那块板）；不得改 `src/core/` 下的事务实现；不得把"主机模型通过"混称"实机通过"。
- 板级脚本 `nor_restore.py` 是宿主机侧工具，修它不需要重烧固件。

## 3. 现象

- 第一次全片演练在 **477/512**（93.16%）停住：日志无 `BLOCK_OK`，`_confirm()` 把该块判成"设备没接受"，脚本退出。
- 单块探针实测：写 `ack=1` 后 +0.156 s 读到 `BUSY/ack=1`；+0.875 s 读到 `BLOCK_OK(0x3)/ack=0`。
- 固件侧擦写一块 32 KiB 约 **0.8 s**；而端到端每块 10 s。差距说明瓶颈不在 flash。
- 第二次演练启动后 49/512 被杀：退出码 0（来自 `tee`），`manifest.json` 不存在，`events.jsonl` 仅 49 行。

## 4. 排查过程

| 步骤 | 我怀疑什么 | 做了什么 | 结果 |
|---|---|---|---|
| 1 | 固件擦写太慢导致超时 | 单块探针按时间戳读头 | 擦写 0.8 s，不是慢的那一段 |
| 2 | 是写→读之间的间隔太长 | 打完 `ack=1` 立刻读头 | 间隔仅 11 ms，推翻猜测 |
| 3 | 读头自身耗时 | 记录每次读头起止 | 末期单次读头 0.875 s，跨过整个 BUSY 窗口 |
| 4 | `_confirm()` 判定太窄 | 读它接受哪些状态 | 只接受 `{BUSY,DONE}`，且只读一次 → 已完成的 `BLOCK_OK` 被判成"没接受" |
| 5 | 第二次演练为何被杀 | 看事件与退出码 | 每块 `unlink()` 一个临时 bin，第 50 次触发宿主 safe-delete 守卫 |

**转折点**：第 3 步——读头耗时（0.875 s）与固件擦写耗时（0.8 s）几乎相等，说明"读得太慢、恰好读在 BUSY 结束之后"，而不是设备拒绝。

## 5. 根因

1. 三个宿主机侧缺陷叠加：`_confirm()` 截止太短且只采样一次；对"头撕裂"没有防护；`finish()` 只读一次 DONE 头。
2. 演练驱动每块删一个临时文件，触发宿主的批量删除确认阈值——**证据链断裂的真实原因是工具守卫，不是固件**。

## 6. 修复

- `host/nor_restore.py`：`_confirm()` 改 10 s 截止循环 + 连续两次读头全等（防 40 字节头撕裂）+ 接受 `BLOCK_OK` 且 ack 已清为"已完成"；`set_u32(ack)` 只容忍日志能证明"本地址本值已发 + 错误正是已知回读不符"的失败（CubeProgrammer 2.23.0 的 `-nv` 并不抑制 `-w32` 回读，固件清 ack 会让 CLI 报 `Failed to download data!`，但字已写入）；`finish()` 读两次 DONE 头并拒绝混合快照。
- 演练驱动：全程复用**一个** `blk-<tag>-scratch.bin`，零 `unlink`，去掉 exists 自锁。

## 7. 验证

**T1（实机，16 MiB 全片）**

| 项 | 值 |
|---|---|
| 块数 | 512 / 512，事件覆盖 0..16 MiB 无缝隙无重叠 |
| 器件 CRC32 | `0xA4188821` == 镜像 CRC == 2026-11-03 金标 |
| 总时长 | 5236.3 s（87 分 16 秒），平均 10.22 s/块 |
| 验收脚本 | `build-temp/drill_accept.py` → `verdict: PASSED`，exit 0（金标 CRC 硬编码，不读器件自报） |
| 守卫/临时文件 | safe-delete 触发 0 次，scratch 1 个 |

**T3（实机，只读）** 烧 `explorer_ZG_uart_READONLY.bin`（43912 B）到 `0x08000000`，COM9 115200 抓一次完整启动：

```
device_id=0x00000413      flash_bytes=0x00100000
hclk_hz=0x0A037A00        jedec_id=0x00EF4018
nor_status=0x00000000     nor_bytes=0x01000000
nor_read_crc32=0x0D968558
NOR driver probe+dry read ok
NOR program/erase hooks compiled in, update engine still gated
```

- **独立交叉核对**：离线金标 `pass1.bin` 前 256 字节的 CRC32 也是 `0x0D968558`。这条不是"固件自己说成功"，而是"器件内容与离线快照同段一致"。
- EEPROM 256 字节 CRC `0x29058C73`，与 11-02 记录一致（内容 00..FF，未写过的裸片）。
- 烧写前已把内部 Flash 前 64 KiB 备份为 `internal-64k-before-explorer.bin`（65536 B，sha256 `cb367229…`，SP `0x20020000`，复位向量 `0x08002BB9`）。

**T4 闸门（目标构建）**：`run_explorer_checks.py` 现在跑 8 个编译变体——除原有 4 个 NOR 写能力变体外，新增"两开关都在才通过 / 只开产品开关被拒 / 只开板级开关被拒 / 开了更新但没写钩子被拒"。四套目标 46 个 C 对象 0 告警，GNU 四套镜像重新链接（16176 / 43912 / 16172 / 43912 B）。

## 8. 学到

- **端到端时间要拆开算**。10 s/块 ≠ flash 慢：8.9 s 是 SWD 传 32 KiB，0.8 s 才是擦写。把"总时间"当成"器件性能"会一路查错方向。
- **确认逻辑要接受"已经完成"这个状态**。轮询只承认"正在忙/已完成"两种状态，却在读头跨越窗口后只采样一次，等价于把"完成了"当成"没接受"。
- **验证要拿离线参照物，而不是器件自报**。器件说 `crc_match=true` 只能证明它自洽；拿 crc32(golden[0:256]) 去比才叫外部证据。
- 驱动"能写"和"允许写"必须是两个开关。只翻产品开关就编译失败，比写在注释里可靠。

## 9. 可写进简历的表述

> 用 512 块增量恢复把 16 MiB SPI NOR 全片重写回已知状态，实测 87 分钟跑满、器件 CRC32 与离线金标一致（`0xA4188821`），并用独立验收脚本（硬编码金标、逐块校验覆盖区间）确认结果，而不是依赖固件自报；同时把产品级 W25Q128 驱动接入板级 BSP，用"器件读回 256 字节 CRC32 == 离线快照同段 CRC32（`0x0D968558`）"证明读通路在真实硅片上正确。

## 10. 边界与未做

- T1 只是**恢复**通路跑通；写入通路（`0x34/0x36/0x37`）仍未接，产品代码至今没有写过 NOR。
- 本次上板只用只读镜像：`storage_verified=0`，启动不发 WREN、不复位、不写状态寄存器。
- 物理 CAN 只做了引脚初始化（日志 `CAN: normal physical 500 kbit/s`），**没有任何总线收发**，USB-CAN 未到货。
- `hardware_verified` 只对"读 + 探测"成立；写入、断电、App 交接、IWDG 都还没做。
- Keil ARMASM/armlink 在本机仍无法启动，全部目标链接走 GNU Arm GCC 15.2.1，`keil_target_linked=false` 未变。
