# 第一次通过产品路径真写 NOR：0x34 擦槽、0x36 写 256 字节、0x37 按设计拒绝

- 日期：2026-11-05
- 类型：实机验证 / 缺陷（期望值算错）
- 关键词：uds, 0x34, 0x36, 0x37, spi-nor, w25q128, crc32, linux
- 可写进简历：Y

## 1. 一句话

第一次用产品自己的 UDS 下载路径改动外部 NOR：`0x34` 擦掉 1 MiB 下载槽（13.7 s）、`0x36` 写入
256 字节（0.17 s）、`0x37` 因包头非法被 `NRC 0x72` 拒绝；随后器件自算的整片 CRC32 与
"金标 + 槽擦除 + 偏移 0 处 256 字节 0xA5"的预测逐字节相等（`0x9C5F9DED`）。

## 2. 背景与约束

到这一步为止，板上所有 NOR 写都是 `stages/board-lab/firmware/w25q_bench.c` 干的，那个文件
自己写着"NOT the product flash path"。产品驱动 `src/driver/spi_nor.c` 虽然已经在 T3 接进 BSP，
但只是被启动时的只读探测用过。T5 阶段 B 要回答的问题是：
**产品自己的 UDS 下载链路，真的能把字节写到硅片上吗？**

约束：不进入"有效包"路径。`0x37` 会在包头/签名校验通过后把状态推到 `UPDATE_READY`，
bootloader 下次启动就会去安装它。用一个假包去做"证明能写"的实验，是在拿板子赌。

## 3. 现象

第一次跑完立刻做全片扫描，`crc_match: false`：

```
image_crc32  (我的预测) 0xEA31D039
device_crc32 (器件实算) 0x9C5F9DED
```

差得很干净——不是随机噪声，是"某段内容与我的模型不一致"。

## 4. 排查过程

先怀疑三类：写没落地、写到了别的偏移、擦除范围不对。

1. `0x36` 明确回了 `76 01`，而 `handle_transfer_data()` 只有在 `p.write()` 返回 0 时才回正响应，
   并且失败会记 DTC、回 `NRC 0x72`。所以"没落地"基本可以排除。
2. 写偏移来自 `s->dl_offset + s->dl_written`，`dl_offset = DOWNLOAD_OFFSET = 0`。
3. 剩下就是擦除范围。`0x34` 调的是 `erase(DOWNLOAD_OFFSET, EXT_IMAGE_SLOT_SIZE)`。
   我算期望镜像时按 **2 MiB** 抹的——因为我记的是"外部前 2 MiB 是新镜像区/旧备份区"。

问题就出在这句话的颗粒度：**"前 2 MiB"是两个 1 MiB 槽**（`EXT_IMAGE_SLOT_SIZE = 0x00100000`，
`EXT_FLASH_TOTAL_SIZE = 2 × EXT_IMAGE_SLOT_SIZE`），不是一个 2 MiB 的槽。
按 1 MiB 重算期望：`0x9C5F9DED`，与器件值完全一致。

## 5. 根因

不是固件错，是我的**期望模型**错：常量就在 `include/ota/flash_layout.h` 里，
我却凭记忆写了一个数字进测试脚本。另外，`EXT_FLASH_TOTAL_SIZE` 只有 2 MiB 而芯片是 16 MiB，
这本身也说明"2 MiB"描述的是布局区，不是芯片容量——两个线索都在，但我先信了记忆。

## 6. 修复

`host/uds_write_probe.py` 不再手写槽大小，改成从布局头文件解析：

```python
text = (CORE / "include/ota/flash_layout.h").read_text(encoding="utf-8")
match = re.search(r"#define\s+%s\s+(0x[0-9A-Fa-f]+)" % name, text)
```

同一轮还顺手修了 `build_restore.py` 的 `stage_hashes()`：它把整个 stage 的
`.c/.h/.py/.ld/.ps1` 都算进"固件输入哈希"，于是新增一个主机脚本就会让上板闸门报
"stage inputs changed"（本次是第二次撞，前一次是 `check_environment.py`）。
现在只哈希 `firmware/` 与 `build_restore.py` 本身——闸门要回答的是
"这个二进制是不是这份固件源码产出的"，不是"目录里有没有文件动过"。

## 7. 验证

实机（`evidence/uds-stage-b/stage-b.json` + `evidence/nor-range/`）：

| 步骤 | 响应 | 耗时 |
|---|---|---|
| `10 02` | `50 02 00 32 01 F4` | 0.01 s |
| `27 01` / `27 02 <key>` | `67 01 5E E9 79 B1` / `67 02` | 0.02 s |
| `22 02 00`（前） | `62 02 00 01 00 …`（metadata 存在、state=0） | 0.06 s |
| `34 00 44 08010000 00000100` | `74 20 02 00`（最大块 512） | **13.72 s**（擦 1 MiB / 256 扇区） |
| `36 01 <256 B>` | `76 01` | 0.17 s |
| `37` | `NRC 0x72`（包头非法，按设计） | 0.03 s |
| 全片 CRC 扫描 | `0x9C5F9DED` = 预测值 | 66.2 s |

全片 CRC 相等这句话的含金量：它同时证明了 1 MiB 槽确实被擦成 0xFF、256 字节落在偏移 0、
以及**槽外面 15 MiB 一个字节没动**。

跑完把 1 MiB 槽按金标定向恢复（32 块），再全片扫描回到 `0xA4188821`。

## 8. 学到的东西

- **"CRC 不等"先怀疑自己的期望值**，尤其是期望值里含手工抄的常量。器件算的 CRC 是
  关于整片硅片的强陈述，我的 Python 模型只是个假设，两者冲突时假设更容易错。
- 布局常量要**从源头取**（正则读头文件），不要从记忆里取。这一条在大项目里就是
  "生成的配置不要手抄"。
- 验证"能写"时**故意让包校验失败**，比造一个假的有效包安全得多：写路径照样被走完
  （擦、编程、读回），但状态机不会进入 `UPDATE_READY`，bootloader 也没机会去装一个垃圾 App。
- 闸门的哈希范围要覆盖"产出二进制的输入"，不是"目录内容"。范围过宽的闸门会被绕过，
  因为人会学会"先重建一次再干活"，那时闸门就只剩仪式。

## 9. 简历表述

在 STM32F407 + W25Q128 上用产品自身的 UDS 下载链路（0x34/0x36，安全访问 seed-key）
完成首次真实外部 Flash 写入，并用"器件自算 16 MiB CRC = 预测镜像 CRC"的方式
证明擦除范围、写入偏移与槽外数据不变（0x37 走拒绝路径以验证失败安全）。

## 10. 边界与未解决

- `0x37` 走的是**拒绝**路径，因此没有真正生成 `UPDATE_READY` 包，也没有触发 bootloader 安装。
- `0x34` 已经把 EEPROM 元数据写成 `UPDATE_DOWNLOADING`（`22 02 00` 可读到 state=1），
  EEPROM 目前没有恢复工具；这是刻意接受的状态。
- "写 256 字节"不等于"能写一整包"：多块 `0x36`、计数回绕、重复块去重、整包签名校验都还没在实机跑过。
- 断电只在一处：无。真实拔电（T11）仍未做。
