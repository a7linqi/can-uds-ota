### [ ] T1 定位并修掉握手停住，把 512 块跑满

**为什么先做它**：这是"升级中断可恢复"这条卖点的地基。整片恢复跑不通，后面写坏了没兜底。

**前置**：板上电 → 复位 → 重烧 `stages/board-lab/` 产出的 `nor_restore_WRITE.bin`（13 636 B，sha256 `1f09cb0c…`）

**已完成（2026-11-05 上午）**

- 预检 `check_environment.py`：**17 ok / 0 missing / 0 warning**，ST-Link + CH340(COM9) 在位。
- 结构化日志复核：`ack=0x1de` 确实写到 `0x200003d4` 且 CLI `returncode=0`，排除「写入失败」。
- **推翻昨晚的关键误读**：`23:20:36.439 → 23:20:36.450` 相隔 **11 ms**；0.877 s 是读头命令自身耗时，不是等待间隔。
- 单块上板探针：`BUSY/ack=1` → 约 **0.8 s** → `BLOCK_OK/ack=0`。设备做完一块只要零点几秒，10 s/块里 8.9 s 是 SWD 传数据。
- 根因：晚期一次慢读横跨 BUSY 窗口，回来是完成态 `0x3`；`_confirm()` 只接受 `{BUSY, DONE}`，把「做完了」判成「没接受」。

**修复**（`host/nor_restore.py`，固件零改动）：`_confirm` 改双读一致 + 接受 `BLOCK_OK`；`set_u32` 容错按真实日志收窄（`-nv` 实测无效）；`finish` 拒绝撕裂 DONE 头。
**验证**：selftest 三项全过、模拟 512 块 13.328 s、真机 3 块 10.14/10.08/10.11 s 全过、构建产物 elf/bin/map 逐字节不变故未重烧。
**进行中**：512 块全程演练 08:24 启动，约 86 分钟；结束后跑 `build-temp/drill_accept.py` 验收。

下面保留昨晚的观测判据表作为历史记录，其中「0.877 s 是间隔」的表述已被上面的实测推翻。

| 观测结果 | 结论 | 下一步 |
|---|---|---|
| ack 保持 478，status 变 1 | 固件正常消费，主机 `_confirm` 判据错了 | 改主机，见下面第 1 条 |
| ack 变 0，status 仍 3 | 有别的路径在清 ack | 回头查固件状态机，别改主机 |
| ack 变 0，status 变 1 | 正常，问题只在主机读得太早 | 改主机，见下面第 1、3 条 |

**修复（三处已定位，都在 `stages/board-lab/host/nor_restore.py`）**

1. `_confirm()` L421-424：accepted 集合 `{BUSY, DONE}` **漏了 `BLOCK_OK(3)`**，而且只读一次。
   改成"循环读到 `ack == 0` 才算设备消费"，status 只要不是 ERROR 就继续等。
2. `set_u32(..., tolerate=True)` L341-346：会连"根本没写进去"一起吞掉。写完必须回读确认。
3. `_refresh()` L309-319：单次读 40 字节无一致性校验，这就是 verify 那次 `DONE offset 0x0` 的来源。
   改成连读两次、`magic/seq/offset/status` 全等才采信。

**重跑**

```
python stages/board-lab/host/nor_restore.py --hardware --mode restore --image <金标 pass1.bin>
```

约 85 分钟（477 块实测 79 分钟）。

**验收**

退出码 0，且 `manifest.json` 里 `status=passed`、`device_crc32=0xA4188821`、512 条事件 offset 无缝铺满 16 MiB。

## 4. P2 —— 补全项（不阻塞主线）

### [x] T9 实现 `0x19` 读 DTC / `0x14` 清除 DTC（**2026-11-05 完成 RAM 版**）

**实际做法**：范围收窄到 RAM（`uds_server_t` 里 8 条表 + `dtc_count` + `dtc_dropped`），理由是 `boot_context_t` 没有 `eeprom_port_t`，持久化必须动 `metadata.c` 的双副本+序号+CRC+commit 末写，一个诊断服务不值得碰核心存储。`0x19` 支持子功能 `0x01`（数量，格式 `0x01`）与 `0x02`（按状态掩码列表），`0x14` 只接受 `FFFFFF`，其余组回 `0x31`；响应放不下时先算容量、回 NRC `0x14`，绝不截断、不越界。
四类 DTC 都从真实失败路径写入：`0xC10400` 安全 3 次错密钥锁定、`0xC10300` `0x34`/`0x37` 元数据读写失败、`0xC10100` `0x34` 擦除失败与 `0x36` 写失败、`0xC10200` `0x37` 与例程 `0001` 的包校验失败。
红 **3348 / 37** → 绿 **3385 / 0**（两套容量一致），420 断电场景不变；四道闸门全过；证据快照重刷 84.7 s、`status=passed`、130 个源码哈希。
**未做**：持久化到 EEPROM/NOR、`0x19` 其它子功能（`0x04`/`0x06`/`0x0A`）、真实 CAN/UART 链路上的实测、PC 工具（`uds_gui.py` / `uds_tool.py`）里的 DTC 页。

2026-11-05 复核：`uds.c` 分派了 9 个服务（含 `0x3E`），但**全仓 `grep -rn dtc/DTC` 零命中** ——
既没有 DTC 数据结构，也没有存储字段、状态掩码或持久化位置。所以这不是"补两个 case"，
第一步要先定：DTC 存在哪（RAM / EEPROM 元数据区 / 外部 NOR）、掉电是否保留、
状态位与快照要不要做。

`0x19` 子功能至少支持 `0x02`（按状态掩码读 DTC），`0x14` 支持 `0xFFFFFF`（全清）。
按约束 `src/core/` 不得引入 HAL，存储要经 `ota_port_t` 抽象，不能直接在 `uds.c` 里写寄存器。
