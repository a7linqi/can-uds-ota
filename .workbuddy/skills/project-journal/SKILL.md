# 项目开发记录（project-journal）

## 什么时候必须写

以下任一情况发生，**在当轮结束前**写一条记录，不要攒着：

1. 新增/修改了一个功能（哪怕只改一个函数，只要行为变了）
2. 修好了一个缺陷（尤其是"只有真机/只有压力下才出现"的）
3. 做了一个技术选型或设计决策（例如"为什么用 32 KiB 块""为什么不做续传"）
4. 排掉了一个环境/工具链的坑（驱动、跳线、电压、权限）
5. 推翻了自己之前的判断（**必须写**，这是最有价值的一类）

不要写的：格式化、改注释、重命名、纯文档措辞调整。

## 写在哪

```
journal/
  README.md          用法说明（不复改）
  TEMPLATE.md        模板（照抄结构）
  INDEX.md           索引表：每写一条就加一行
  entries/YYYY-MM-DD-<短横线英文标题>.md
```

同一天多条时文件名加后缀区分，例如 `2026-11-04-uart-bringup.md`。

## 必填结构（照 TEMPLATE.md）

1. **一句话**：这条记录在解决什么问题
2. **背景/约束**：为什么这件事必须做、有什么不能动的边界
3. **现象**：可观察到的、别人能复现的描述（带数字）
4. **排查过程**：试过什么、排除了什么、**哪一步是转折点**
5. **根因**：一句话说清机制，不要只说"有 bug"
6. **修复**：改了哪些文件、关键改法、为什么这样改而不是别的改法
7. **验证**：命令 + 期望 + 实际；没验证的必须写"未验证"
8. **学到的东西**：能讲给别人听的原理层结论（2–4 条）
9. **简历表述**：1–2 句可直接用的话，必须含动词 + 技术 + 可量化结果
10. **边界/未解决**：什么没做、什么还没证明

## 硬性要求

- **数字必须来自当场实测**；没测过就写"未实测"，不许估一个写成实测。
- 区分验证等级：主机模型 / 目标构建 / 实机。三者不可混称。
- 失败与弯路要留：写"我先怀疑 X，量了 Y 才发现不是"，比只写正确路径更有复习价值。
- 每条记录 ≤ 100 行，宁可分两条。

## 写完顺手做

1. 在 `journal/INDEX.md` 末尾加一行（日期｜类型｜标题｜关键词｜可写进简历 Y/N）
2. 如果这条推翻了旧结论，在旧记录顶部加一行 `> 已被 YYYY-MM-DD 的记录推翻：…`
3. 如果影响到项目状态，同步更新 `stages/board-lab/STATUS.md` 或 `CAN_UDS_HANDOFF.md`

## 简历取材口径

面试前只看 `INDEX.md` 里"可写进简历 = Y"的行，再打开对应记录的第 9 节。
每条记录的第 9 节应该能直接回答："你做了什么、怎么证明的、数字是多少"。
不允许出现"参与了""负责了"这类无法追问的表述。
