# 断电实验证据（实机）

三轮真实断电，同一块板（STM32F407ZGT6 + W25Q128 + 24C02）。
判定原则：不把没测到的写成测到；探针失联不算 0 V；空结果不算结论。

## 实验一：空闲态断电（2026-11-05 下午）

状态 `IDLE / v15 / 44824 B / application / seq 122`，无任何写操作进行中。
用户拔掉全部三路供电（适配器 + ST-Link USB + 串口 USB）。

- 整条 USB 链路消失 **16.5 s**（监视时间线 `+481.17 s → +497.70 s`）
- 塌陷瞬间最后一次有效电压读数 **2.87 V**（正常 3.24 V），随后 ST-Link 自己失联
- **没有 0 V 实测**：探针与被测对象共用同一条 USB，见证者一起消失
- 恢复后 `IDLE / v15 / 44824 B / application / seq 122`，与断电前逐字段相同
- EEPROM 读成功、未触发 I2C 锁死（role=application 即旁证：锁死会停在 loader）

结论边界：这**不是**"升级中断可恢复"的证据——断电时一个字节都没在写。
监视工具：`host/power_cycle_watch.py`（单串口句柄 + 2 Hz `3E 00` + 3 s SWD 电压）。

## 实验二：下载中途断电（2026-11-05 晚，本轮）

起点 `IDLE / v15 / 44824 B / application / seq 137`（脚本先经 `10 02` 交棒进 loader）。
驱动脚本：`host/power_cut_upgrade.py`，证据 `evidence/power-cut-interrupt/`。

时间线（脚本内相对秒）：

| t | 事件 |
|---|---|
| 0.5–6.9 | `10 02` 交棒 → `11 01` → loader 横幅 → `10 02` → `27` 解锁 → 状态确认 v15/seq137 |
| 6.9–66.9 | 60 s 倒计时，每 2 s 发 `3E 00` 保活（S3 为 5 s，见"教训"） |
| 67.0 | 发 `0x34`，擦除外部 NOR 下载槽 |
| 81.3 | `0x34` 正响应 `74 20 02 00`（擦除耗时 **14.23 s**），元数据已落 DOWNLOADING（seq 137→138） |
| 67–88 | 连续发 `0x36` 数据帧（510 B/帧，共 89 帧计划） |
| **88.2** | **拔电**：串口写入失败，此时已下载 **9690 B（19/89 帧）** |
| 147.6 | 用户恢复供电，串口重开（断电约 50 s，含 USB 重枚举） |
| 157.1 | 显式 DTR/RTS 复位后完整横幅：loader 探测 NOR/EEPROM 全部正常 → `handing off to the app at 08010000` |
| 168.8 | 判定 **RECOVERED** |

恢复判据（四条全部满足）：

1. 状态 DID：`role=application`，active v15 / 44824 B——loader 验签后跳回了原固件
2. SWD 读回 `0x08010000` 44824 B，**与构建产物逐字节相同**（sha256 `47f604c1…`）
3. 96 B 签名凭证在位（`0x080FFFA0`，签名非零）
4. 元数据 seq 只 +1（就是 `0x34` 那次 DOWNLOADING 落盘），恢复启动本身零写入

### 恢复后的状态语义

断电时元数据停在 `DOWNLOADING`（半事务状态，pending 字段尚未写入——`0x37` 验签
通过后才会写）。恢复后板子**跳过挂起的事务直接跑原固件**；下一次升级的 `0x34`
直接重启事务（见实验三），不需要人工清理。这是"可重做安装"设计的直接体现。

### 本轮的教训（第一次尝试失败的根因）

第一次运行 `0x34` 被正当拒绝 NRC `0x22`：解锁后脚本空等 60 s 倒计时才发 `0x34`，
而 `uds_poll()` 的 **S3 超时（5 s）同时清掉编程会话与安全解锁**。`uds_stage_d.py`
从未暴露此问题，因为它解锁后立刻发 `0x34`。修法：倒计时期间每 2 s 发 `3E 00`
（任何请求都刷新 `last_request_ms`）。同轮还修了把 `0x36` 的 NRC 误判成"断电"
的分类错误——NRC 是协议应答，端口写入失败才是断电。

## 实验三：中断后立即完整升级（闭环）

在同一块刚被断电打断过的板子上、从挂起的 DOWNLOADING 状态直接重新升级 v17：

`34 → 74`（事务重启）→ 89 帧 `36` 全正响应 → `37 → 77`（Ed25519 验签通过）
→ `31 01 00 01 → 71 ... 00` → `11 01` → 擦装 960 KiB → 跳转。

最终：**`IDLE / application / v17 / 44824 B / min_ver 17 / seq 146`**。
证据：`evidence/power-cut-interrupt/upgrade-v17-after-cut/stage-d.json`。

## 实验四：安装中途断电（2026-11-05 夜，本轮）

项目最后一块空白：**断电落在 `11 01` 复位后的安装窗口里**——旧 App 正被擦除、
新镜像写到一半、凭证尚未写入的 ~8 秒。证据 `evidence/power-cut-install/`（文件
来源见其中 `FILES.md`），权威判决在 `evidence/power-cut-install-settled/recovery.json`。

起点 `IDLE / application / v18 / 44824 B / seq 156`。`power_cut_upgrade.py --cut-phase install`：
交棒 → 解锁 → 倒计时 → `34`（14.25 s）→ 89 帧 `36` → `37 → 77`（v19 验签通过，状态落 READY）
→ `11 01` 复位 → 监视原始串口，banner 出现 `loader: selecting boot target` 即判定窗口开启。

| t（窗口内） | 事件 |
|---|---|
| 0 s | `selecting boot target` 出现，窗口开启（此时开始备份 v18 到 NOR 备份槽） |
| ~2 s 起 | loader 擦内部 960 KiB App 槽 |
| **3–4 s** | **拔电**：3 s 提示打印后串口句柄即死（第 4 s 提示未出现） |
| ~+40 s | 三路供电插回 |

恢复（无任何人工干预，板子自己完成）：

- 冷启动横幅未被捕获（取证脚本开端口晚于横幅；板子正静默重做安装）——这是工具时序
  问题，不是板子行为；显式复位后的横幅完整捕获了整条链：`selecting boot target` →
  `handing off to the app at 08010000` → App 横幅 `awaiting real health checks`
- 状态 DID：**`IDLE / application / v19 / 44824 B / seq 162`**，pending 已清（App 自己确认）
- SWD 读回 `0x08010000` 44824 B，**与构建产物逐字节相同**（sha256 `47f604c1…`）
- 96 B 凭证在位，且凭证内签名 **等于 v19 升级包尾部签名**（`2e93f593c132f9ab…`），
  凭证头 v19 / 44824 / crc `0xD6B888DB` / flags=1——证明跑的正是断电时安装到一半的那个镜像

语义：断电时旧 App 已被破坏（无凭证即不可启动），但 NOR 下载槽里验过签的 v19 还在、
备份已写好；loader 的 READY/INSTALLING 分支幂等重做安装，终态不仅"活着"，而且
**带着正确凭证跑在断电时正在装的那个版本上**。下载中断（实验二）保住旧固件，
安装中断（本实验）自己装完新固件——两条恢复路径都实机闭环了。

### 本轮的教训（两次工具事故）

1. **第一次窗口错过**：`PULL NOW` 只打在后台终端，操作者看不到。30 s 无操作后安装
   正常完成（板子进了 v18）。修法：实验节奏改为"助手在聊天里发拔电信号"。
   意外收获：`install-window-uart.bin` 保留了**未被打断的完整安装窗口参考序列**。
2. **断电检测后脚本崩溃**：串口句柄已死时恢复 `ser.timeout` 触发重新配置端口抛
   `PermissionError`，JSON 未落盘、恢复阶段未执行。修法：try/except 包住超时恢复。
   证据靠终端时间线手工补录（`cut-transcript.txt`）。
3. **恢复取证撞上静默自愈**：重开端口时板子正忙于重做安装，状态请求超时、SWD 读回
   `Data read failed`、冷启动横幅 0 字节。修法：状态读重试 5 次、SWD 转储前等 3 s
   并重试一次、横幅静默期从 1 s 延长到 3 s（签名验证期间控制台静默 1–2 s，
   1 s 窗口恰好把 `handing off` 那行剪掉）。教训：**恢复证据要收两轮——事件瞬间一轮、
   稳定态一轮**，第一轮的"失败"可能只是板子在忙。

## 仍未覆盖（诚实边界）

- 本轮没有电压采样（没跑 SWD 电压监视），断电判据是串口句柄死亡 + 时间线
- 恢复横幅来自重开端口后的显式 DTR/RTS 复位，**不是**断电后的第一次冷启动
  （第一次冷启动发生在端口重开之前，横幅未被捕获；重开时读到 0 字节）
- 横幅里的 `nor_read_crc32` 只是探针小样本 CRC，不覆盖下载槽，两次同值不代表
  擦除没发生（擦除证据是 `0x34` 的 14.23 s 耗时与正响应）
- "拔掉三根线"是拔线，不是拨板载开关；开关是否控制电轨仍是 unknown
